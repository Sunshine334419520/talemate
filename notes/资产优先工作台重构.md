# 资产优先：小说工作台重构方案（草案）

> **职责**：回答"design_spec 为什么显得多余、删掉之后资产长什么样、Agent 如何从'流程驱动'退回'按需协作'"。
> **读者**：要决定产品形态与下手顺序的人；实现资产层、工具面、桌面工作台的人。
> **状态**：2026-11-24 · **草案，尚未拍板**，不含实现。本文只描述目标与迁移路径。
> **相邻**：`docs/product.md`（产品边界）· `docs/design-docs.md`（现行四层与两段式）· `notes/小说Agent双轴矩阵.md`（能力矩阵诊断）· `docs/ui.md`（桌面现状）

## 0. 一句话

**design_spec 多余，不是因为"结构知识"多余，而是因为它同时当了注册表、模板校验器和工作流。**

删掉它换不来"用户自己管理资产"——那需要一个真正的**资产层**：世界观条目、角色、概览、大纲与节拍、章节、伏笔、状态，都是用户可空、可建、可改、可排序、可删的东西；Agent 只在被叫到时读写它们，审阅是一条通用变更通道，不是一套阶段门。

## 1. 诊断：为什么现在像"被流程推着走"

### 1.1 design_spec 把三件事绑成一个模块

`src/framework/design_spec.ts`（373 行）同时干三件事：

| 角色 | 在代码里 | 产品含义 |
|---|---|---|
| **种类与寻址** | `SPECS` 按路径 glob 登记 core / world / characters / outline-vol / outline-seq（`design_spec.ts:67-318`） | 哪种文档在哪儿、叫什么、list 里怎么显示 |
| **模板与必填** | 每份规范的 `sections`（该有哪些 `##`、每格写什么、别写什么）；角色的必有五格在 `characters.CHARACTER_FIELDS`，由 `invariants.ts` 的 `characters.skeleton-complete` / `required-kept` 强制 | 不按模板组织的文档**落不了盘**（提案被拒或整篇写被拒） |
| **工作法（流程）** | 每份规范尾部的 `guide` / `WORK_METHOD`：让用户讲 → 起草 → `propose-design` → 回话 → `apply-design`；并配套 `enter-draft` 是"三向审阅的唯一通道" | 模型被要求**领读一个流程**，而不是按用户请求干活 |

用户反对的是第二、三件事，不是第一件。但三者绑在一起，所以现在"删 design_spec"会被理解成"删掉结构知识"。

### 1.2 资产没有自己的位置，所以只能由 Agent 造

现在仓库里只有"文件"这一层抽象：

- 桌面端只有三个文档 IPC：`docs:tree` / `docs:text` / `docs:save`（`desktop/src/main/index.ts:460-480`）——**没有新建、删除、重命名、排序**。
- CLI 只有一个 `/design <name>` 打印某份文档（`src/cli.ts:527-533`）——**没有按资产类型新建/删除的命令**。
- 所以"建一个角色/一卷大纲/一个世界条目"的唯一合法路径，就是让 mate 走 `design-spec` 拿形状 → `propose-design` → `apply-design`。用户不是不会写，是**没有手**。

这正是"过于执着写作流程"的机制来源：不是 prompt 写坏了，是**没有资产入口时，流程就是唯一的入口**。

### 1.3 模板被升级成了硬门槛

- `propose-design` 的 `reviewable` 要求：有规范的文档必须按规范的小节组织，否则拒绝（`design-docs.md:87-90`）。
- 角色卡缺任一必有格即拒（`characters.skeleton-complete`），卡上出现 `##` 即拒（`characters.no-shallow-heading`）。
- 结果：用户想用自己的方式写角色卡（一张自由笔记、一个更简单的表）会被工具拒绝；而"自由长尾"只允许在五格**之后**加东西。

模板是**工艺建议**，如今成了**通行证**。这是"设计"变成负担的直接原因。

### 1.4 流程写进了工具契约，而不是 prompt 建议

| 位置 | 内容 |
|---|---|
| `prompts/tools/enter-draft.txt` | 写整篇设计稿前必须进草稿模式，否则没有三向审阅 |
| `prompts/tools/enter-prose.txt` / `exit-prose.txt` | 写正文前必须切到正文模式 |
| `prompts/tools/task.txt` | "规划者返回后，下一步工具调用**必须**是 propose-plan" |
| `prompts/tools/propose-plan.txt` | 规划是一章的前置步骤，交出去就停（halt） |
| `prompts/tools/propose-design.txt` | 整篇设计文档只许走这条提案路 |
| `docs/agents.md` 的工作协议 | 把"设计段/写作段"写成 mate 的固定动作序列 |

模型没有"不按这条流程做"的合法路径。用户可以打断它，但每次都要跟流程对抗——这就是"执着"的体感。

### 1.5 该保留的判据

本文不推翻这些（它们与流程无关，是质量与安全）：

- **用户看过的字节 == 落盘的字节**（预写 diff / 提案审阅）。这比"先写后回退"强，见 §4.4。
- `write_ops` 单一写路径、CAS、原子写、权限分类、每轮改动记录。
- 正文由 mate 自己写，不派 writer；不做评审 Agent；版本靠 git。
- 上下文**现读**，绝不缓存旧设定。

## 2. reveric 是怎么做的（事实，不评价）

reveric 是 Flutter + Drift 的桌面写作应用。它的重心不是"生成"，是**一个作者长期维护的工作台**。

### 2.1 资产是数据库里的一等实体

| 资产 | 表（`lib/shared/database/novel_content_database.dart`） | 关键字段 |
|---|---|---|
| **角色** | `CharacterProfiles:441` | name / role / gender / aliases / tags / identity / age / motivation / arc / appearance / description / biography / personality / behaviorTags（情境→行为）/ currentState / firstAppearChapterId / 软删 |
| **章节** | `Chapters:563`（表名 `chapter_nodes`） | 树：type=`volume/chapter/extra`、parentId、siblingOrder；title；**outline（写前）**；**brief（写后总结，不覆盖 outline）**；content；wordCount；stat=`draft/published`；tension；emotion；events（编年史者抽的跨章事件）；comments（作者划词批注） |
| **世界观/材料** | `Documents:889` | type / title / content / category / tags / parentId / isFolder / sortOrder —— 一棵通用文档树 |
| **大纲** | `Outlines:929` + `OutlineBeats:959` | outline：documentId / title / content / status / startChapterNum；beat：title / content / status（pending/in_progress/finished）/ **chapterCount** / sortOrder |
| **伏笔** | `Foreshadowings:624` | title / setup / payoff / setupChapterId / payoffChapterId / status |
| **图鉴** | `Items:525` | type（faction/creature/item/skill）/ title / content / category |
| **关系** | `EntityRelations:1111` | source/target（type+id）/ relationType / chapterId / sceneId / proof |
| **故事状态** | `NovelStates:824` + `NovelStateSnapshots:843` | 键值 + 每次写入生成一份 Markdown 快照（chronicler / user） |
| **改动** | `WorkingChanges:739` + `ChangeCommits:782` | resourcePath/Type/Id、field、oldText/newText、baseVersion、status、**sourceTurnId** |

### 2.2 用户拥有工作台

- 侧栏分组（`lib/shared/models/novel_workspace.dart:145-167`）：概览 / 实体图 / 故事进展 / 画布 / 封面 / 章节 / 大纲 / 角色 / 伏笔 / 素材 / 世界观 / 地图 / 图鉴（势力·生物·物品·技能）/ 会话 / Agent 规则。
- **只读的只有三个**：概览、实体图、故事进展（`novel_workspace.dart:12-17`）；其余全部可增删改。
- 新建：章节与大纲先建空记录再进编辑；角色/世界/伏笔/图鉴走"延迟创建"（`selection.isCreating`，内联表单，不写库直到保存）。
- **新书是空工作台**，没有"必须先设定再大纲再写"的强制顺序；只有软提示（`docs/solutions/heuristic-onboarding.md`）和未保存提醒。

### 2.3 大纲与节拍：篇幅是看得见的东西

- 大纲编辑页 = 上部正文 Markdown + 下部**时间轴**：beat 卡片按 `chapterCount` 的宽度排在章数刻度尺上，可拖拽重排；每张卡三个 chip：序号、状态、章数（`lib/desktop/widgets/workspace/outline_timeline_strip.dart`，子代理读取）。
- **章与 beat 没有外键**：`startChapterNum` + 逐 beat 累计 `chapterCount` 做位置映射（同文件 `:304-320`）。这是刻意的弱耦合——改章数不用改每章的外键。
- 效果：用户不用解析散文大纲就知道"这一卷多少章、哪一段占几章"；Agent 也读得到同一份结构。

### 2.4 AI 是"带工具的协作者"，不是流程引擎

- **工具面**（`lib/shared/services/ai/tools.dart:3750-3788`）：`Read` / `Glob` / `Grep` / `Create` / `Write` / `Edit` / `Replace` / `Remove` / `GraphSearch` / `SpawnAgent` / `ForkAgent` / `AskUser` / `TodoWrite` / `AgentSkill`。
- **寻址是资源路径**：`/characters/{id}`、`/lore/{title}`、`/outlines/{title}`、`/chapters/{id}`（`novel_workspace.dart:43-104`）；重资产不进 system prompt，只发一条 `<system-remind path=… hint=…>`，模型自己 `Read`（`chat_session_controller.dart` 侧，子代理读取）。
- **改动是变更集**：AI 先写入，记 `working_change(active, baseVersion, old/new text, sourceTurnId)`；轮末默认 auto-accept 并 commit；UI 是"最近变更日志 + 逐条回退 + 回退到本轮之前"（`docs/solutions/chat-changes-rework.md:9-16, 53-58, 119-121`）。
- **已发布章节锁正文**：只有连续性字段可写（outline / brief / tension / emotion / events），正文与标题锁死（`lib/shared/services/ai/tools_write.dart:57-69, 525-533`）。
- **规则优先**：用户规则（`AgentRule`）是 per-novel 的，注入时声明优先级高于默认行为；"未要求写入时不要改库、未要求开写时不写大纲或正文"写在编排提示里（`assets/prompts/agent/orchestrator.md`）。

### 2.5 它也有流程——但流程是"用户触发 + 可跳过"

- 唯一硬流程是**审查闭环**（正文先写入 → 委派审查 SubAgent → 最多 2 轮修正 → 仍不行就 AskUser），用户可以规则/明确要求跳过（`orchestrator.md` 的"审查闭环"）。
- 另有一道 **setup_phase 门**：新书、规则为空、会话 ≤3 轮时，要求先立写作规则再写大纲/正文（`orchestrator.md` 的 `{{#setup_phase}}`）。
- 默认接受意味着**应用前没有预览**；散文字段无法三方合并，回退是字段级整体倒回——这是它自己承认的妥协（`chat-changes-rework.md` 的"已知妥协"）。

### 2.6 不能照搬的部分

| 不抄 | 理由 |
|---|---|
| 全结构化 DB 作为唯一真源 | talemate 是 markdown + git + 路径寻址的产品；DB 会把"可读、可 diff、可手改"换掉 |
| 写后默认接受 | 与"用户看过的字节 == 落盘的字节"冲突；talemate 的预写 diff 更强 |
| 审查 SubAgent / 多专家 Agent | 与 talemate 已拍板的"不做评审 Agent"直接冲突 |
| 关系图谱 + proof、图鉴共用 Items、画布/分镜/封面 | 是它的内容形态（视频/剧本/多媒介），不是写作 Agent 的最小集 |
| 三栏 + 浮动面板的信息架构 | 我们是 CLI + 桌面壳，信息架构要另设 |

## 3. 目标形态：资产优先

### 3.1 五条原则

1. **资产归用户。** 可空（一本书可以只有一句话简介）、可自由（模板可选，不按模板也能落盘）、可管理（新建 / 改名 / 排序 / 删除 / 改状态），不经过 Agent 也能完成。
2. **Agent 是协作者，不是流程引擎。** 生成、改写、补全都发生在"用户要"之后；没有它自己启动的阶段，也没有"必须先做 A 才能做 B"。
3. **审阅是变更，不是阶段。** 写前 diff（或整篇预览）+ 本轮改动 + 回退；没有草稿模式、没有正文模式。
4. **结构知识可选。** 模板、写作 skill、事后诊断三种载体，均不阻塞落盘。
5. **保留底线。** 预写审阅、CAS / 原子写 / 权限分类、正文自己写、不派评审、现读不缓存、版本靠 git。

### 3.2 资产清单（已定，载体见 `docs/assets.md`）

| 资产 | 寻址（项目相对） | 用户可做 | Agent 可做 |
|---|---|---|---|
| **作品 / 概览** | `design/brief.md` | 改题材、一句话简介、基调、文风 | 按用户话整理、提建议 |
| **世界观条目** | `design/wiki/<题>.md` | 新建、改、拆专题页 | 起草、补细节、查冲突（读） |
| **角色** | `design/characters/<名>.md` | 新建、改、删、排序 | 起草、试镜台词、改一格 |
| **大纲** | `design/outline/<名>.md` | 新建多份（总纲/卷/线）、改名、排序 | 起草、补节拍、改一格 |
| **节拍** | `design/outline/<大纲>/beats/b<NN>.md` | 增删、拖拽、状态、预计章数 | 读、改、按拍写章 |
| **章节** | `chapters/*.md` | 新建、写、改、标记发布 | 写正文、改稿（发布后锁正文） |
| **伏笔** | `state/foreshadowing.md` 或独立条目 | 登记、改状态 | 提议埋/收（用户拍板） |
| **状态** | `state/…` | 改 | 每章后回写（可选步骤） |
| **材料 / 专题** | `design/<…>` | 自由建 | 读（未登记种类，按普通文档） |

> 与现在相比只多两样：**概览**成为独立资产（现在塞在 core 的格子里）、**节拍**成为独立文件（现在只是一份散文）。其余是"从文件升级成资产"。

### 3.3 载体：markdown + 可选 frontmatter，索引现算

**推荐**：文件仍是唯一真源；**frontmatter 只放机器字段**（`kind` / `title` / `order` / `status` / `aliases` / `links`），正文完全自由。

```md
---
kind: character
title: 沈越
order: 3
status: active
aliases: [沈老三]
---
# 沈越

（自由正文。想按模板写就写五格，不想就写一段话。）
```

- 资产索引（"这本书有哪些角色、哪几卷、每卷几个节拍"）**每次从文件现算**，不落第二份——沿用仓库那条"能算的不存"。
- 旧项目无 frontmatter：**kind 由路径推断**（`design/characters/*` → 角色），零迁移即可读；写回时补 frontmatter 是可选的"整理"动作，不是强制的。
- 为什么不用 JSON/DB：会丢掉"用户手改、git diff、Agent 按 markdown 读"三件事；reveric 用 DB 是它的 UI 形态决定的，不是写作本身的必然。

### 3.4 节拍：独立文件，挂在大纲上（已拍板）

一拍一个文件：`design/outline/<大纲名>/beats/b<NN>.md`，头部写归属与篇幅：

```md
---
kind: beat
title: 进内城
outline: design/outline/第1卷.md   ← 归属的唯一真相
order: 2
chapters: 3                        ← 预计几章
status: pending
---
这一拍发生什么。
```

- 路径由大纲派生（`design/outline/第1卷.md` → `design/outline/第1卷/beats/`），但**归属由
  `outline` 字段说了算**：路径只是排布，头才是真相。
- 大纲文件里**不存节拍清单**，也不存"第几章发生什么"——两份清单就是两份真相。
- 章范围现算：`大纲.startChapter` + 按 `order` 累计各自 `chapters`；改某一拍的章数，后面每一拍
  自动跟着变。解析与计算只有一处（`framework/assets.ts` 的 `beatsOf` / `chapterRangeOf`）。
- 优点：节拍可单独编辑、可单独审阅、可单独被 Agent 读；不会因为动大纲正文而重排小节。
- 代价：文件数变多；移动大纲不自动搬节拍目录（当前拒绝，让调用方先处理）。
- 备选 "大纲内小节" 与 "sidecar JSON" 都放弃：前者删改一拍要动整份大纲，后者是两份真源。

**章与节拍映射**：写第 M 章时，按上述公式找到覆盖 M 的那一拍，读该拍正文与相邻拍；不做外键。

### 3.5 弱关系，够用就好

- **不做关系图谱**：talemate 已经拍板"关系不进设计文档，属情节素材"（`characters.md:117-128`）；现在也不引入 id 图谱。
- 伏笔用**名字/章号弱引用**（"第 37 章收"），不建外键表。
- 只有"机器必须读"的东西才结构化：节拍的章数与状态、章节的发布状态、角色的名字/别名（list 与 search 用）。
- 判据：**能算的不要存；只有 Agent 与 UI 都要按字段用的，才进 frontmatter。**

### 3.6 Agent 看到的仍是文本

- 每个资产提供"渲染成 markdown"的读视图（reveric 的 `toDocumentContent` 是同一思路）：frontmatter 字段 → 标题与条目，正文原样。
- `list` 给资产清单（种类、标题、一行摘要、节拍数/章数），`read` 给全文或小节，`search` 跨资产。
- 资产不必"加载进" system：常驻只留用户 pin 的两份（默认简介 + 世界总纲）；其余按需读。

## 4. 工具面与流程重排

### 4.1 删除

| 删掉 | 原因 |
|---|---|
| `design-spec` 工具 + `framework_tools` 模块 | 规范不再由模型按需取；模板在 UI / skill 里 |
| `SPECS` / `specFor` / `renderSpec` | 种类由资产注册表（frontmatter/路径）给，形状不再校验 |
| `proposal` 对 spec 的依赖（`reviewable` / `labelOf` / 按格渲染） | 审阅改为整篇/整段 diff，不做"逐格提案" |
| `characters.skeleton-complete` / `required-kept` / `no-shallow-heading` | 必填与 `##` 限制都源于"提案逐格渲染"；审阅变了，判据随之消失 |
| `enter-draft` / `exit-draft` / `enter-prose` / `exit-prose` + mode `draft` | 审阅不再靠模式；正文窗口仍由 harness 注入（保留） |
| `task.txt` 里"返回后必须 propose-plan" | 规划变可选 |
| `propose-design` / `apply-design` 的双工具 + 模式协议 | 合并为"整篇写时先给预览"：整篇 `write` 生成一份预览（同一 write_ops、同一 CAS），用户接受即落盘；不再需要"提案登记 + 模式 + 两工具" |

> 保留 `apply` 的**字节来源保证**（落盘字节 == 用户看过的字节），只是把它从"工具+模式"降成 `write` 的一个行为：整篇写 → 预览 → 接受。局部改仍是 `edit` 的 diff。

### 4.2 新增

| 加什么 | 放在哪 |
|---|---|
| 资产注册表（路径 → 种类 + frontmatter 解析）；种类定义在 `assets/kinds/*.json` | `framework/assetkinds.ts` + `framework/assets.ts` |
| 节拍解析与章映射 | `framework/beats.ts` |
| UI：`assets:create` / `update` / `rename` / `delete` / `reorder` IPC | `desktop/src/main/index.ts` |
| CLI：`/new <kind> [name]`、`/assets`（清单） | `src/cli.ts` |
| 章节状态（draft/published）+ 发布锁正文 | `write_ops` 规则表 |
| 轮次回退（已有写前快照 + 本轮改动，补一个 revert 原语） | `session/` + 桌面 |
| 空工作台建议卡（软 onboarding，不阻塞） | 桌面 / CLI 首屏 |

### 4.3 默认路径：用户说什么，就做什么

```
"写第 N 章"        → mate 现读资产 →（可选规划）→ 写正文（diff 审阅）→（可选状态回写）
"建个角色 / 补世界观" → mate 读现状 → 写整篇（预览）或改一格（diff）
"看看大纲 / 设定"    → list / read
"这一段改改"        → edit（diff）
```

- **没有强制前置**：缺角色卡也能写正文（卡是约束，不是签证）。
- **规划可选**：mate 觉得材料不够、或用户要"先规划"，才走规划；规划是普通工件（`.talemate/plans/`），不是门。项目设置里可写"写前先规划"偏好。
- **状态回写可选**：写完提示"要不要把这一章的变化写回现状"，用户点头再做。

### 4.4 审阅：保留预写 diff，补轮次回退

| | talemate（保留） | reveric（不抄） |
|---|---|---|
| 应用前 | **diff / 整篇预览，用户点头才落盘** | 直接写入，事后变更日志 |
| 轮末 | 本轮改动卡（已有） | commit + 日志 |
| 回退 | 写前快照 + 用户消息回退（已有"仅对话/连文件"） | 逐条/整轮回退 |
| 冲突 | CAS（已有） | 字段级检测 + 显式提示 |

结论：**不学"先写后审"**；把 reveric 的"轮次回退"补进来就够（"回退到这一轮开始前"已经有一半实现）。

## 5. design_spec 的知识去向

`SPECS` 里的内容有真价值（角色写成矛盾、卷的六格、序列的出口/不可逆转折、禁揭……）。删模块不等于删知识，三个去处：

1. **新建模板**：UI/CLI 新建资产时提供"空白 / 按模板"；模板正文就是现在 SPECS 里的 sections 与 guide。模板只影响初始内容，之后怎么改都行。
2. **写作 skill**：`skills/` 里放"角色卡怎么写 / 卷纲怎么写 / 节拍怎么排"的知识卡，用户让 Agent 帮忙时才加载（经 `<available_skills>` 的 description 触发）；不参与落盘校验。
3. **事后诊断（后续）**：写完可以问"这份大纲缺什么"，Agent 读模板给建议——**只读、只提示、不拒绝**。

一句话：**把"通行证"降级成"参考书"。**
