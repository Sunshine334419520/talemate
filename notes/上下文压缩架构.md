# 上下文压缩架构（Context Fold）

> **读法**：§1–§2 是诊断与第一原则；§3–§9 是架构本体；§10–§13 是工程落点（破坏性重构、分阶段、验收）。可以只读 §2、§3、§6 判断方向，其余是执行细节。
>
> **状态**：设计提案，尚未落地。落地后应拆成 `docs/compaction.md`（现状）与本文（历史决策）。

---

## 0. 一句话

**压缩不是"把旧对话缩成一段摘要"，而是"把上下文按生命周期分层，每层用不同的保留策略"**。

现在的实现把所有东西都压在同一个动作里：把窗口折成一条 `summary + recent`。这既压掉了不该压的（用户决定、工具结论），又没压该压的（常驻设定、system 体积），还把唯一能恢复的材料路径丢了。新架构要把这件事拆开：

```
固定常驻的 → 每轮现读，不进压缩
悬而未决的 → harness 状态，每轮注入，不进压缩
刚发生的   → 原文保留，按 turn 整段淘汰
对话里的   → LLM 累积折叠（只折对话，不折书）
读过什么的 → 确定性证据账（路径 + 小节 + rev）
拍过板的   → 确定性决定账（用户原话）
```

---

## 1. 现在的压缩为什么不对

代码事实见 `src/session/compaction.ts`、`src/context/assemble.ts`、`src/storage/session-store.ts`。五个洞：

1. **第二次压缩丢上一份摘要**：`headText` 只认 user/assistant，compaction 落到 `return ""`。窗口又以最新 compaction 为起点，旧摘要既不在输入也不在窗口。
2. **工具输出完全不参与摘要**：`read`、`search`、`task`、`recall` 的结果都是 tool part；摘要只取 assistant 的 `text`。规划者的整份简报、刚读到的设定，压一次就没了。
3. **`recent` 不是消息，是纯文本**：`recent` 6 条转成 `[user]/[assistant]` 文本塞进 compaction 消息，tool part 和工具入参全丢；而窗口从 compaction 起步，那 6 条原文并不在窗口里。
4. **规划正文不可读**：计划只活在内存 `pending` 和 `.talemate/plans/`；后者不在语料根表里，`read/glob/grep` 够不着。压缩或重启之后，系统仍要求"照规划执行"，但模型读不到规划。
5. **system 超限时压缩无能为力**：`isOverBudget` 用 `lastInput`（含 system+tools）判超，但 `compact()` 只动 messages。常驻设定本身过大时，每一步都触发压缩，永远修不好；窗口 ≤ 6 条时还直接 `return null`。

根因不是实现细节，是**把"对话记录"当成了"项目记忆"**。这本书的记忆本来就在 `design/`、`chapters/`、`state/`、`.talemate/plans/` 里；对话里真正不可恢复的，只有用户的意图、否决理由、以及与文件无关的临时上下文。把书压进 600 字摘要，既压不下，也不可信。

## 2. 第一原则（不变量）

1. **磁盘是长期记忆，对话不是。** 压缩只保留"磁盘上没有"的东西：意图、决定、未决问题、正在进行的任务。
2. **能算的不要存，能读的不要摘要。** 故事到哪了、欠什么、谁在哪，从 `state/` 与正文现取；摘要是投影，不是第二份 canon。
3. **摘要只增不减。** 第 n 次折叠的输入必须包含第 n-1 次的摘要；不允许从零重写。
4. **结构性内容不经生成。** 用户拍板、未答提问、批准的计划、状态快照由 harness 格式化；LLM 只写"对话叙事"。
5. **工具调用与结果不可分。** 最小压缩单位是 turn；一个 assistant step 的 tool call + result 永远同进同出。
6. **压缩失败等于没压缩。** 一次折叠是一条原子事件；摘要生成失败时窗口不变。
7. **先截断，后压缩。** 单次工具输出在工具边界就有上限；压缩是最后一道，不是第一道。
8. **预算按 token，分到层。** system / tools / working set / summary 各有预算；system 超限时不进入压缩循环。
9. **每次折叠可解释。** 进/出 token、压掉几段、保留几条证据、哪些材料被丢弃——都能在 trace 里看到。
10. **摘要不是 canon。** 渲染时明说"书的事实以项目文件为准；需要时按证据账重读"。

## 3. 分层模型

每一轮送给模型的上下文，由五层组成；只有 L2/L3 会被压缩。

```
┌──────────────────────────────────────────────────────────────┐
│ system                                                       │
│  L0 固定层   env · role system · AGENTS.md · skill 目录       │
│  L0 常驻层   design/core.md + design/wiki/world.md           │
│              （每轮现读，带 rev，有字符预算）                  │
│  L1 任务层   待审提案 · 已批准计划 · 未答提问 · 当前模式       │
│  L1 正文窗   正文规范 + 文风卡 + 本章规划全文                  │
├──────────────────────────────────────────────────────────────┤
│ messages                                                     │
│  L3 对话史   <context-state>                                 │
│               ├─ <project>   位置 / 承诺 / 当前计划（派生）    │
│               ├─ <session>   累积折叠（LLM）                  │
│               ├─ <decisions> 用户拍板原文（确定性）            │
│               ├─ <evidence>  读过什么 @rev（确定性）           │
│               └─ <open>      未决问题（确定性）                │
│  L2 工作集   最近 N 个 turn 的原文（结构完整，tool part 在）   │
│  L3/当前     本轮用户消息                                     │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 内容 | 谁写 | 生命周期 | 压缩策略 |
|---|---|---|---|---|
| **L0 固定** | system 外壳、AGENTS.md、skill 目录 | harness | 每轮重建 | 不压 |
| **L0 常驻** | core / world 全文 | 文件 | 每轮现读 | 不压，但限体积 |
| **L1 任务态** | 提案、计划、提问、模式 | harness | 跨轮、可持久化 | 不压 |
| **L1 正文窗** | 规范、文风、本章规划 | harness | 写正文期间 | 不压 |
| **L2 工作集** | 最近对话原文 | 事件投影 | 高水位内保留 | 按 turn 整段淘汰 |
| **L3 对话史** | 累积摘要 + 三个确定性账 | harness + summarizer | 全会话 | 累积折叠 |
| **磁盘** | design / chapters / state / plans | 用户与 mate | 永久 | 不进上下文，按需重读 |

关键边界：**L2 以下不承载书的事实**。如果一条事实重要到下一章还要用，它应该已经在 `state/`、`design/`、`chapters/` 或规划里；摘要只负责"我们聊到哪了、用户要什么、还欠哪个决定"。

## 4. 压缩单位：turn，不是 message

当前实现按消息条数切（`RECENT_KEEP = 6`），而一条 assistant 消息可能带十个工具结果。6 条既可能只是一轮，也可能是六轮。新设计按**语义段**切：

```
user message        = 一个 segment
assistant step      = 一个 segment（该 StoredMessage 的全部 parts，含 tool call/result）
turn                = 一个 user message + 其后的全部 assistant steps，直到下一个 user
```

规则：

1. **压缩单位是 turn**，从最老的一端开始整段淘汰。Q/A 不拆开。
2. **当前 turn 永不压缩**；最近 `recentFloor`（按 token，不按条数）内的 turn 原文保留。
3. **单个 turn 超预算**时，允许"段内修剪"：把它的工具结果换成摘要+指针，保留 user 全文、assistant 文本、最后一步。这是唯一允许拆 turn 的情况，且必须在 trace 里标 `intraTurn: true`。
4. **未闭合的 segment 不压**：`running` 状态的工具、被中断的 assistant、还没 commit 的消息都跳过。
5. **跨 user 的边界是天然的折叠点**；assistant step 内部不是。

`StoredMessage` 已经把 tool call 与 result 放在同一条 assistant 消息的 `parts` 里，所以"原子性"在存储层已经成立；压缩只需不拆消息。

## 5. 折叠算法

一次折叠分五步。前两步是确定性的，第三步才用模型，第四步校验，第五步原子提交。

### 5.1 触发

```ts
usable   = contextWindow(model) - maxOutputTokens - safetyTokens
highWater = usable * 0.85
lowWater  = usable * 0.50
```

- 上次请求的真实 `usage.input` 优先；没有真数时用字符估算（按中英分别加权，见 §7）。
- **迟滞**：越过 highWater 才折叠，一次折到 lowWater 以下。避免当前实现"每步都压一次"的抖动。
- 触发点在每步请求前；一次折叠后重新量，仍超则继续折（换模型到小窗口时可能要多轮）。

### 5.2 选择（确定性）

```ts
function select(messages, budget): { segments: Segment[]; keep: Segment[] } {
  let kept = lastTurnsWithin(tokens: budget.recentFloor);   // 先保住最近
  let rest = messages.slice(0, -kept.length);
  let picked = [];
  while (estimate(picked) < budget.overflow && rest.length) {
    picked.push(rest.shift());                              // 从最老整 turn 取
  }
  return { segments: picked, keep: [...rest, ...kept] };
}
```

选不中任何东西、而 system 又没超 → 抛"窗口不足且无可压缩段"，带具体数字给界面。**不允许静默跳过、继续发一个超窗请求。**

### 5.3 构造折叠输入（确定性）

```xml
<fold-input>
  <previous-fold>          ← 第 n-1 次的摘要，原文照带，不重写
    <session>…</session>
  </previous-fold>
  <pinned>                 ← 全部由 harness 从文件/事件生成
    <project>写到第 12 章；第 12 章收在……</project>
    <promises>未回收：……</promises>
    <decisions>…用户原话…</decisions>
    <plan chapter="13" path=".talemate/plans/ch_13.md" hash="…"/>
  </pinned>
  <segment turn="7-11">
    [user] …
    [assistant] …
    [tool kind="read" path="state/foreshadowing.md" rev="a1b2c3" chars="812"] 摘要：…
    [tool kind="task" agent="planner" chars="5230"] 结论：…（结论型输出保留正文，上限 4k）
  </segment>
</fold-input>
```

工具结果分两类处理：

- **原始材料**（read / search / webfetch / recall 列表）：只给**指针 + 首段**，不给全文；正文可由 `path#section@rev` 重读。
- **结论**（task 的 `<task_result>`、recall 的结论、一次 research 的最终答复）：给正文，按字符上限截断。结论是"感知的产物"，不是可重读的原文；压掉它等于压掉取证结果。

### 5.4 生成与校验

summarizer 只输出对话叙事，固定四段：

```xml
<accomplished>这段里做成了什么（≤3 条）</accomplished>
<intent>用户想要什么、否过什么、在等什么（≤3 条）</intent>
<open>尚未解决、下一步要用的问题（≤5 条）</open>
<pointers>下一步可能需要的路径/章号（≤5 条）</pointers>
```

校验（不通过则重试一次，再失败走降级）：

- 四段齐全，总长 ≤ `summaryBudget`（初始 1200 token）；
- 不出现"（待定）"以外的空洞；
- `<intent>` 里不得复述 `<decisions>` 已有的内容（重复不算错，但浪费预算，校验只警告）；
- 不得包含路径之外的新专名（启发式：与 pinned/project 文本比对，未知专名只警告，不判失败——避免误杀）。

**摘要不是唯一产物。** 同一份折叠记录还带：

- `pinned`：上面那组确定性块，原样渲染；
- `evidence`：本段新增的读证据（去重：同 path#section 只留最新 rev）；
- `decisions`：本段产生的用户拍板（来自 canonical 事件，不来自模型）；
- `open`：来自 harness 的可回答提问 + `<open>` 段的并集；
- `budget` / `dropped`：这次压掉了什么。

### 5.5 原子提交

一次折叠 = 一条 canonical 事件 `context/compaction`，带完整记录。投影规则：

```
窗口 = [<context-state> 合成消息] + consumed.toSeq 之后的全部原文消息
```

- 摘要生成失败 → 不写事件，旧窗口继续；下一次重试。
- 进程崩溃在"生成了、没写事件"→ 旧窗口仍然完整；没有半截状态。
- 旧格式兼容：读到 `role:"compaction"` 的旧消息时，把它当作 `legacy: true` 的折叠记录，后续折叠可继续累积。

## 6. 摘要的累积折叠

这是修掉 P0-1 的核心。折叠是**左结合**的：

```
S₀ = 空
Sₙ = fold(Sₙ₋₁, segmentₙ, pinnedₙ)
```

不是 `Sₙ = summarize(segmentₙ)`。实现上 `<previous-fold>` 必须原样进入 summarizer 输入；`pinned` 每轮重建（它来自文件，不来自上一次摘要）。

### 6.1 为什么 pinned 不能交给模型

模型会漂移、会漏名字、会把"打算"写成"已经发生"。pinned 里的东西是确定的，应该**复制**而不是**生成**：

| pinned 块 | 来源 | 是否生成 |
|---|---|---|
| `<project>` 位置 | `state/progress.md` 最后 7 节 | 否，原文 |
| `<promises>` 未回收 | `state/foreshadowing.md` 过滤状态 | 否，原文 |
| `<decisions>` | `proposal/decision` 等事件 | 否，用户原话 |
| `<plan>` | 已批准规划（路径 + hash） | 否，harness 读取 |
| `<evidence>` | 工具调用事件 | 否，确定性派生 |
| `<session>` | summarizer | 是，唯一一段 |

这同时解决"600 字承载整本书"的问题：摘要只承载对话，书的规模由文件承载。

### 6.2 摘要满了怎么办

单条 `<session>` 超过 1200 token 时，不把整段重新压一遍，而是：

1. 只把 `<session>` 最老的一半折进一个 `<archive>` 短块（≤300 token），保留最近一半；
2. `<archive>` 同样累积，不重写；
3. 如果 `<archive>` 也满，才做一次"两级合并"。

这是可选的第二级；第一版不需要。先保证"只增不减 + 有上限"，再观察实际会话长度。

### 6.3 渲染

`<context-state>` 作为窗口里第一条 user 消息：

```xml
<context-state>
  <project>第 12 章已落盘。上一章收在……</project>
  <promises>未回收：…（见 state/foreshadowing.md）</promises>
  <session>…累积摘要…</session>
  <decisions>用户否决了"让林晚主动认罪"的方案；理由：太早亮底牌。</decisions>
  <evidence>
    read design/characters/林晚.md @9f2c1a
    read state/progress.md @77ab02
    task planner session=… (2026-11-21)
  </evidence>
  <open>1. 第 13 章是否引入新角色？用户未答。</open>
</context-state>
（以上是上一段对话的投影。书的事实以项目文件为准；不确定时按上面的路径重读。）
```

关键变化：**它不再自称"故事摘要"**。它明确是"对话投影 + 恢复坐标"。

## 7. 预算

### 7.1 token 估算

字符估算只能当兜底。建议：

```
cjk   = 中日韩字符数 × 1.0
ascii = 其余字符数 × 0.28
tokens ≈ cjk + ascii + 4 × 消息条数 + tool schema 字符 × 0.3
```

优先级：

1. 上一次请求的真实 `usage.input`（ground truth）；
2. `request/header` 里记录的三段字符数按上述公式估；
3. 全新会话、还没发过请求 → 用公式估 system + tools + messages。

`lastInput` 只用于**总量**判断；分层预算用估算值。界面上显示的百分比继续带"约"。

### 7.2 分层预算（初始值，按评测调）

| 层 | 占 usable 上限 | 超限行为 |
|---|---|---|
| system（含常驻） | 40% | preflight 报错，要求拆 world.md / 换模型 |
| tools schema | 15% | 报错（工具太多是配置问题） |
| `<context-state>` | 10% | 先折 `<session>`，再截 `<evidence>` |
| working set | ≥ 40% | 低于此则折叠 |

### 7.3 system 超限（P0-4）

折叠前先算 `systemTokens + toolSchemaTokens`：

- 若 `> usable * 0.55`：不折叠，直接返回可操作的错误——"常驻设定 18.2 万字，约占模型窗口 92%；请把 `world.md` 拆成 wiki 专题页，或换更大窗口的模型"。
- 若 `> usable`：第一次请求都不发。当前实现会先发一个必超的请求，或在 `lastInput` 上无限触发压缩。

常驻文档本身要有体积预算：`core.md` 建议 ≤ 8k 字符，`world.md` ≤ 30k 字符。超了在 `list` 与启动检查里提示，不静默截断（截断常驻设定会让模型读到半条规则，比没有更糟）。

## 8. 先截断，后压缩

压缩不应该为工具输出擦屁股。工具边界先做预算：

| 工具 | 上限 | 超限返回 |
|---|---|---|
| `read`（无 section） | 12k 字符 | 标题索引 + 首段 + "用 section=… 读某一节"；超长 section 支持 `offset` 分页 |
| `read`（有 section） | 12k 字符 | 第一节 + "此节还有 N 字，用 offset=… 继续" |
| `search` | 40 条命中 | "命中 N 处，显示前 40；用 path 缩小范围" |
| `list` | 80 行 | 文档树 + "还有 N 份" |
| `webfetch` | 80k（已有） | 已有 |
| `task` | 结论全文，≤ 12k | 超限截断并标注 |
| `recall` | 目录 / 单条 | 已有 |

另外两条感知卫生：

1. **常驻文档去重**：`read` 读到 `core.md` / `world.md` 且没指定 section 时，返回"已在常驻层 @rev；要读某一节用 section"，避免同一份设定在上下文里出现两次。
2. **证据账替代全文留存**：一次 `read` 的全文只需要活到当前 turn 结束；之后由 `path#section@rev` 代表它。模型要细节就重读。

## 9. 任务态与计划：L1 必须持久化

当前 `pending` 只在内存（`Session.pending`），重启清空；规划正文在 `.talemate/plans/`，但 `read/list/search` 读不到。新架构：

### 9.1 计划

- `propose-plan` 落盘后，追加 canonical 事件 `proposal/presented`（chapter / path / hash / 摘要行）。
- 用户接受/拒绝追加 `proposal/decision`（accept / reject / refine + 用户原话若有）。
- 会话打开时，从事件重建 `pending`；计划正文由 **harness** 读 `.talemate/plans/ch_N.md`（不进模型工具），hash 不符时标 `stale`。
- **正文窗口直接注入已批准计划全文**。它是有界的、用户看过的那份字节；和文风卡一样，属于"这一章写作必须成立的约束"。

这修掉的不只是压缩问题：重启后 `enter-prose` 不再因为 `pending` 清空而失效。

### 9.2 决定账

accept/reject 是按钮，不产生用户消息，所以现在压一次就只剩 assistant 的转述。新增事件：

```ts
"proposal/decision": {
  proposal: string;        // 路径或 PLAN_KEY
  verdict: "accept" | "reject" | "refine";
  note?: string;           // refine 时用户原话
  chapter?: number;
}
"ask/answered" / "ask/pending" // 已有提问结构，补齐事件
```

决定账从事件派生，随每次折叠累积，原文保留（refine 原话、reject 理由）。这是"作者否过什么"的第一等载体，不需要等 `state/failures.md`。

### 9.3 重启恢复

| 状态 | 现状 | 新架构 |
|---|---|---|
| 待审文档提案 | 内存，重启丢 | 事件重建（或明确丢弃，走重新提案） |
| 已批准规划 | 内存，重启丢 | 事件 + 文件，重启恢复 |
| 未答提问 | journal 已有 | 保留，进 `<open>` |
| 模式 | 内存（文档明说临时） | 保持临时；计划可恢复即可重新 enter-prose |
| 计划正文 | `.talemate` 不可读 | 正文窗口由 harness 注入 |

## 10. 失败、降级与原子性

### 10.1 三档降级

| 档 | 条件 | 行为 |
|---|---|---|
| **normal** | summarizer 正常 | 摘要 + pinned + 证据账 |
| **degraded** | summarizer 报错 / 超时 / 输出校验失败 | **确定性折叠**：只把被压段的工具结果换成指针，保留 user/assistant 文本；不生成任何叙事。标 `degraded: true` |
| **refuse** | system 超限 / 无可压段 | 不写事件，不继续请求；把数字和动作给界面 |

`degraded` 的意义：宁可少一段叙事，也不要编一段；下一次窗口有余量时再做正常折叠。

### 10.2 原子性

折叠记录只通过一条 `context/compaction` 事件落盘；消息不删不改。投影是纯函数：

```
project(events) → { stateMessage, workingSet }
```

- 写到一半崩溃 → 事件日志里没有这条，窗口回到旧状态。
- 同一次折叠重复执行 → 以 `consumed.toSeq` + `previousId` 去重，幂等。
- 回退/分支 → 回退事件之后，后续折叠记录也在被遮住的范围内，投影自然回到更早的窗口。

### 10.3 换模型

- 新窗口小于当前用量：先按新预算折叠，再发请求。
- 折叠后 system 仍超：报错，不静默截断。
- 模型表（`context/windows`）继续是人工维护的唯一表，但增加 `maxOutput` 与 `safety`。

## 12. 重构落点

### 12.1 新模块

```
src/context/
  budget.ts       窗口表 + token 估算 + 分层预算 + 触发/迟滞
  segments.ts     StoredMessage -> turn/step 段；选择；原子性；段内修剪
  fold.ts         编排：preflight -> select -> build -> summarize -> validate -> commit
  summary.ts      折叠输入构造、summarizer 调用、四段输出解析与校验
  ledger.ts       证据账 / 决定账 / 未决问题（从事件与工具 part 确定性派生）
  project_state.ts state/progress、foreshadowing、计划的结构化注入
  assemble.ts     渲染 ContextPlan -> system + NeutralMsg[]（取代 toNeutralMessages）
```

### 12.2 删除/替换

| 现在 | 处理 |
|---|---|
| `session/compaction.ts` 的 `estimateChars` / `headText` / `recentText` | 删除；由 `budget` + `summary` + `segments` 取代 |
| `StoredMessage.role: "compaction"` | 折叠改为事件；旧消息保留为 `legacy` 投影，迁移期后删除该 role |
| `loadModelWindow` 的"从 compaction 起" | 投影按 `consumed.toSeq` 决定窗口；原文消息不拍平 |
| `compaction/summary` 事件 | 由 `context/compaction` 取代；旧事件兼容读 |
| `.talemate/plans` 不可读 | 不进语料根表；由 harness 在正文窗口注入，工具仍读不到 |
| `RECENT_KEEP = 6` | 改为 `recentFloor` token 预算 |
| `prompts/summarizer.system.txt` | 重写为"折叠对话"，不再写"story-state / 设定 / 伏笔" |

### 12.3 数据模型（跨层放 `core/types.ts`）

```ts
export interface CompactionRecord {
  id: string;
  at: number;
  previousId?: string;
  legacy?: boolean;
  consumed: { fromSeq: number; toSeq: number; turns: number; intraTurn?: boolean };
  summarizer?: { model: string; promptHash: string; schema: number };
  summary: { session: string; open: string[]; pointers: string[] };
  pinned: {
    project?: string;
    promises?: string;
    decisions: DecisionEntry[];
    plan?: { chapter: number; path: string; hash: string };
    resident: Array<{ path: string; rev: string }>;
  };
  evidence: EvidenceEntry[];
  budget: { usable: number; trigger: number; before: number; after: number };
  dropped: { messages: number; toolResults: number; toolChars: number };
  degraded: boolean;
}

export interface EvidenceEntry {
  kind: "read" | "search" | "task" | "recall" | "skill" | "web";
  path?: string;
  section?: string;
  rev?: string;
  label: string;          // 工具/子代理/skill 名
  chars: number;
  digest?: string;        // 结论型输出的一行
}

export interface DecisionEntry {
  at: number;
  proposal: string;
  verdict: "accept" | "reject" | "refine";
  note?: string;
  chapter?: number;
}
```

`CompactionRecord` 是 canonical 记录；`<context-state>` 是它 + 当前任务态的渲染结果。

### 12.4 新事件

```ts
"context/compaction": CompactionRecord;
"proposal/presented": { proposal: string; chapter?: number; path?: string; hash?: string };
"proposal/decision": DecisionEntry;
```

`proposal/presented` / `proposal/decision` 不只服务压缩：界面回看、评测、`state/failures.md` 的后续都靠它。

## 13. 分阶段落地

### 阶段 0：止血（不改数据模型，先修四个洞）

1. 累积摘要：`<previous-fold>` 进入 summarizer 输入；测试断言内容包含旧摘要专名。
2. 摘要输入带工具摘要：`read` 给 path@rev + 首段；`task` 给结论正文；`search` 给命中数和 top 路径。
3. `recent` 改为"保留顺序号"：折叠记录存 `toSeq`，窗口从"折叠消息 + toSeq 之后的原文"取；不再拍平。
4. 正文窗口注入已批准计划全文（harness 读文件）。
5. preflight：system + tools 超限时报错，不进入消息压缩。

这五条能立刻消掉 P0-1/2/3/4，且不需要新事件、新模块。

### 阶段 1：结构（新模块与记录）

- `budget` / `segments` / `fold` / `summary` / `ledger` / `project_state` 落地；
- `context/compaction` 事件；
- 确定性证据账与决定账；
- 迟滞与分层预算；
- trace 与界面水位。

### 阶段 2：任务态持久化

- `proposal/presented` / `proposal/decision` 事件；
- 会话打开时重建 pending；
- 重启后计划与正文窗口恢复；
- 旧 `compaction` 消息的 legacy 迁移。

### 阶段 3：取数与卫生

- `read` 分页 / `read` 常驻去重 / `list`/`search` 上限；
- 文档 rev 进 `read` 输出与常驻块；
- 常驻体积预算与 `list`/启动提示。

### 阶段 4：评测与体验

- §11.2 全部用例；
- 折叠提示词定稿；
- 二级归档摘要（只在需要时）；
- `/trace` 的折叠视图。

## 14. 被拒绝的方案

| 方案 | 为什么不做 |
|---|---|
| **向量库 / RAG 作为主记忆** | 文档小、结构清楚、按路径和小节精确寻址；embedding 会丢掉小节与 rev，还会引入不可复现的召回。真到上千章，加"章摘要索引"也比向量库稳 |
| **每轮重新总结整段历史** | 贵、慢、漂移；且会重复总结已经压掉的内容。折叠必须是增量的 |
| **把工具输出全部留在摘要里** | 等于不压缩；工具输出是材料，路径才是可恢复的表示 |
| **让 summarizer 同时维护故事设定与伏笔** | 生成物不可审计；设定在文件里，摘要在对话里，两者不能混 |
| **新增一个"记忆管理" agent** | 它是隐藏的 harness 能力，不需要用户可见角色；新增 agent 只会让"谁决定保留什么"变得模糊 |
| **摘要当作 canon** | 与两阶段落盘、CAS、"用户看过的字节才落盘"全部冲突 |
| **state 常驻注入** | 每轮为只在写作前有用的东西付钱；改为折叠时快照 + 规划/正文时读取 |
| **压缩时静默丢弃、不记账** | 用户与模型都不知道丢了什么；违反可观测性 |

## 15. 验收标准

架构落地后，下面每一条都必须为真，并有测试钉住：

1. 任意次折叠后，第一次折叠前的用户否决原话仍在 `<decisions>` 里。
2. 任意次折叠后，第一次折叠前的专名仍能从 `<session>` 或 `<project>` 里找回。
3. 折叠后最近一个 turn 的 tool call / result 结构与折叠前一致。
4. 规划被批准后，折叠不会让正文窗口丢失计划全文；重启也不会。
5. 一次折叠只写一条事件；summarizer 失败时窗口字节不变。
6. system 超限时不发请求、不进入压缩循环，给出可操作的错误。
7. 一次折叠后上下文低于 lowWater；下一次请求不再触发。
8. 任何被压掉的工具输出都能由 `<evidence>` 的 path#section@rev 重读；重读结果标出 rev 是否变化。
9. trace 能回答：压掉了多少、保留了什么、为什么现在压。
10. 所有用例离线通过，不需要真实模型。
