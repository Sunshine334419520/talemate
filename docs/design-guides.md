# 设计指南：只给“什么叫好”，不给“必须填哪格”

> **职责**：定义小说设计文档（角色卡、卷纲、序列纲、核心设定、世界观、章规划）怎么被引导、审阅与修改；明确哪些是创作判断，哪些是机器数据。
> **读者**：要改 `src/framework/design_guides.ts`、`src/framework/proposal.ts`、`src/framework/characters.ts`、`src/framework/invariants.ts`、`src/tool/design_tools.ts` 与相关提示词的人。
> **对齐代码**：2026-11-23 · 已落地：指南注册表、整篇/diff 提案、形状不变量删除；旧的全文小节模板已删除。对象与真源见 `information-model.md`。
> **相邻**：`information-model.md`（对象/真源/载体）· `perception.md`（每一步怎么选材料）· `state.md`（状态层）· `characters.md` / `outline.md` / `design-docs.md`（旧文档，其中的“必须按格写”由本文替代）

**一句话**：设计文档是给未来写作的契约；我们告诉模型“一份好文档回答什么问题、什么算烂”，不规定它必须长成几张格子。

---

## 1. 为什么三类文档存在

| 文档 | 约束的尺度 | 一句话 | 写晚了会怎样 |
|---|---|---|---|
| **卷纲** | 一个阶段 | 这一卷结束时什么必须为真 | 章章都不错，卷末发现没走到该到的地方 |
| **序列纲** | 一个情节单元 | 这一小段结束时什么必须为真 | 卷没有中段结构，章规划没有父契约可投影 |
| **角色卡** | 一个反复出场的人 | 他下一次怎么选、怎么说话 | 每场重新即兴，迟早 OOC；事后补卡是墓志铭 |

它们都是**契约**，不是摘要、不是简历、不是事件清单。契约的价值在约束**还没写的东西**。

## 2. 设计指南的形状

```ts
export interface DesignGuide {
  id: string;
  /** 路径 glob：哪种文档用这份指南 */
  match: string;
  /** 这份文档为什么存在；模型先读这一句 */
  purpose: string;
  /** 一份好文档应该回答的问题；不是必填格 */
  questions: string[];
  /** 1–2 段优秀范例（短，不是全文模板） */
  examples: string[];
  /** 常见烂法；模型要能认出自己写的是哪一种 */
  antiPatterns: string[];
  /** 尺寸建议，不是硬截断 */
  size?: string;
  /** 可选的结构建议；模型可以不用 */
  suggestedShape?: string;
  /** `list` 里这一类怎么占一行：铺标题，还是取首句 */
  summary: "headings" | "lead";
}
```

规则：

- **`questions` 是判据，不是 schema。** 模型可以用任何结构回答；只要回答得上，就是好文档。
- **没有 `sections` 必填清单。** 不再因为“没按小节组织”拒绝提案。
- **没有形状不变量。** 不再“缺一格即拒”。
- **`size` 是建议。** 超了提示“这一笔会不会改变某个选择”，不静默截断。
- **审阅看整篇 + diff**，不看逐格编号。

## 3. 角色卡

### purpose

> 写一张“下一次写他时用得上的合同”，不是人物传记。每一笔都应该能改变他在某个情境下的选择或说法。

### questions

1. 他想要什么？具体到能驱动行动。
2. 他最怕什么？恐惧决定压力下的选择。
3. 他绝不做什麼？否定式约束，防 OOC。
4. 他说话是什么声音？给**一句可验伪的原话**。
5. 他身上的矛盾是什么？“既…又…”；这是选择的来源。
6. 他的能力/限制如何塑造选择？能力即性格，不是技能表。
7. 别人怎么称呼他？别名/称谓（grep 与连续性用）。

### 好例子

```markdown
# 角色：林晚

二房庶女，管着家里的账，却始终不被允许坐上主桌。

她想要账册，不是为了钱，是为了让二房在族老面前没法再说她“只是个丫头”。
她最怕被当成二房争产的棋子；所以先算账，再叫人。

“二爷的账，什么时候轮到外人看了？”——她对二房以外的人，永远先问这一句。
她绝不让人看见她哭。
```

### antiPatterns

- 形容词堆（“英俊、冷酷、聪明”）；
- 简历/年表（“三岁丧母，七岁习武”）；
- 当前处境（那在 `state/characters`）；
- 关系（谁欠谁、此刻盟友还是敌人；那在 `state/relations` 或正文）；
- 没有一句可验伪的台词；
- 把“他很强”写成技能列表，而不是选择/限制。

### size

建议 300–1200 字，决策级。不是硬上限；超了提示“这一笔会改变哪一场的选择？”

### 不应该写进卡

- 当前状态（在场/已故/伤势/钱）；
- 谁知道什么（知识边界是命题级 `state/knowledge`）；
- 事件（“他在第 3 章杀了 X”）；
- 关系图（关系是人物对，不是卡）。

## 4. 卷纲

### purpose

> 写这一阶段的**故事合同**：结束时什么不可逆地变了，欠读者什么，什么不能提前揭。不是剧情梗概。

### questions

1. 这一卷的独立故事问题是什么？为什么是现在？和上一卷的差异、未决项、主线增量。
2. 谁想要什么，谁挡着，失败会失去什么？目标、阻力、对手的目标/资源、升级轴、失败代价、本卷上限。
3. 卷末什么**状态**必须为真？用状态写，不用事件写；至少一轴不可逆（信息/关系/资源/位置/认知/力量）。
4. 旧债、新债、禁揭是什么？该兑现/推进/延期的承诺；3–5 条不能提前揭的事。
5. 这一卷分几段、每段的功能是什么？3–6 个序列的功能、不可逆转折、线程、承诺；卷末高潮落在哪一段。
6. 情绪节奏是什么？主情绪、爽点轮换、中点/低谷/高潮、喘息、卷首钩子。（参考，不是合同）

### 好例子

```markdown
这一卷的独立问题是“沈越能不能在沈家站住脚”，不是“他能不能报仇”。

卷首他是被逐出家门的弃子；卷末他成了族老不得不承认的账房先生，但代价是林晚知道遗言。

目标：查清账册。阻力：二房与族老。升级轴：从查账到被当成争产的人。
失败代价：再次被逐出，且失去林晚。本卷上限：不能碰十年前车祸的幕后。

旧债：母亲留下的那封信。新债：账册是抄本。禁揭：十年前车祸的幕后。

序列：混进夜宴（拿账册）→ 账册失窃（被栽赃）→ 族老审账（反转）→ 卷末选择（烧掉抄本保林晚）。

情绪：压抑里偶尔的爽点；卷末不靠打赢，靠选择。
```

### antiPatterns

- 事件清单（“主角遇到老乞丐，拿到地图”）；
- 章号；
- 承诺台账的实际状态（那在 `state/foreshadowing`）；
- 只写打赢/打输，不写代价；
- “这一卷很精彩”这种评价；
- 把序列写成每章的节拍表。

### size

建议 1–2 页。不是硬上限。

## 5. 序列纲

### purpose

> 写这一小段的**单元合同**：入口和出口差在哪，哪一步不可逆，兑现/埋下什么，什么不能写坏。事件可以换，状态不能换。

### questions

1. 这一小段在卷里承担什么功能？推进哪条线程、兑现/埋下哪条承诺。
2. 它自己的问题是什么？谁想要什么、谁挡着、失败会失去什么；必须能脱离整卷单独成立。
3. 入口 → 出口差在哪？入口写关键前提（处境、资源、关系、谁知道什么、什么威胁悬着）；出口写结束时什么是真的，以及如何引出下一段的问题。
4. 哪一步不可逆？从什么变成什么（行动/认知/关系/处境/力量/身份），谁选择，代价是什么。
5. 兑现哪条旧承诺、埋下哪条新承诺、什么不能提前揭？
6. 哪几处不能写坏？世界规则、战力上限、知识边界；哪些事件可以换。
7. 体量大概多少？（参考，不是章数）

### 好例子

```markdown
功能：给沈越一个进内城的理由，并让林晚第一次怀疑他。

入口：沈越有夜宴请帖，但没有账册；林晚以为他是二房的人。
出口：沈越拿到账册抄本，林晚知道他撒谎；“合作”变成互相利用。

不可逆转折：沈越为保账册，把林晚推出去挡了族老的人；她记住了。
承诺：埋下“账册是抄本”；兑现“林晚查沈越的底”。

写法约束：夜宴座次按房头；二房不坐主桌；沈越不能在这里用遗言。
体量：3–5 章。
```

### antiPatterns

- 事件清单（“主角遇到老乞丐”）；
- 章数/节拍表；
- 具体场景调度；
- 把“功能”写成事件（好：给主角一个进内城的理由；坏：主角遇到老乞丐）；
- 出口和入口状态相同（那它们其实是同一个序列）。

### size

建议 300–800 字。不是硬上限。

## 6. 核心设定与世界观

| 文档 | purpose | questions（简） | 结构 |
|---|---|---|---|
| `design/core.md` | 这本书是什么、为什么值得写 | 一句话简介、主角要什么/怕什么、引擎/规则、题材与声音 | 自由散文；常驻 |
| `design/wiki/world.md` + 专题页 | 世界规则与术语 | 这条规则约束什么选择？和哪条规则冲突？谁遵守/谁例外？ | 自由散文 + 索引；一条事实只放一处 |

**world 不再要求固定格。** 一份“世界索引”（专题标题 + 每条规则一行）常驻；正文按场景取。专题页可长可短，但同一事实只放一处。

## 7. 章规划

### purpose

> 写这一章的**执行合同**：这一场必须让什么为真、什么不能提前兑现、要落哪些产物。不是镜头脚本。

### questions

1. 这一章要推进什么？为什么是现在？
2. 这一场：谁在场、各自要什么、谁挡谁、代价是什么？
3. 必须发生什么？（事件/决定/反转，不写镜头）
4. 什么不能提前兑现？哪条禁揭不能碰？
5. 章末留下什么问题？
6. 要落哪些产物？（新卡、世界事实、正文、状态回写）
7. 章型是什么？（过渡/铺垫/小高潮/卷末高潮；由用户/任务参数给，不由文档推断）

### antiPatterns

- 逐步节拍、字数、放大点；
- 只有内心领悟，没有活人对抗；
- 把“必须发生”写成“可以发生”；
- 跳过前置产物直接写正文。

### 章型放哪

**不放进规划文档的必填格。** 它由 `ask-user` 的答案或 `task` 入参提供，作为机器数据；规划正文可以在自然叙述里提到它，但不要求固定字段。

## 8. 怎么引导模型

1. **`design-spec` 返回设计指南**（工具 id 保留，避免工具面 churn）：按路径 glob 返回 `DesignGuide`（purpose/questions/examples/antiPatterns/size），不再返回“必须有哪些小节”。
2. **`propose-design` 提示词**：先说 purpose，再给 questions 与反例；要求“回答这些问题，结构自定；每一笔要能改变某个选择或某句话”。
3. **不做逐格渲染**：提案 = 整篇正文 + 与现文的 diff。
4. **不做形状校验**：只校验路径、权限、CAS、原子写；如果文档用了标题，校验标题不重复（寻址需要），不校验“必须有哪几个标题”。
5. **审阅辅助（可选）**：界面可把指南问题作为侧边清单给用户看，用户可忽略；不做机器判定。
6. **模型自检**：在提交提案前，模型自己对照 questions；缺的可以在给用户的说明里讲，但不要往文档里塞注释。

## 9. 审阅与修改

| 场景 | 路径 | 用户看到 |
|---|---|---|
| 新文档 / 整篇重写 | `propose-design` | 全文 + 与现文的 diff；接受/拒绝/提意见 |
| 局部修改 | `edit`（find/replace，或行范围） | 精确 diff；确认后原子写 |
| 删除 | `delete` | 影响面（引用检查） |
| 状态回写 | `write` / `edit` | diff |

**没有“第 N 格改成 X”。** 审阅单位是 diff/段落/行。用户提意见是自由文本；模型据此改，再给新 diff。

## 10. 机器数据从创作文档里拿出来

| 机器需要 | 放哪 | 不放哪 |
|---|---|---|
| 章型 | `task` 入参 / `ask-user` 答案 | 卷纲/规划的必填格 |
| 承诺状态 | `state/foreshadowing`（独立账本） | 卷纲 |
| 知识边界 | `state/knowledge`（命题 × 人） | 角色卡 |
| 关系 | `state/relations`（人物对） | 角色卡 |
| 场景边界 | 场景索引（派生/缓存） | 正文固定标记 |
| 作者决定 | 事件 + 决定索引（计算） | 创作文档 |
| 别名 | 别名索引 / 卡里一句话 | grep 硬编码 |

原则：**创作文档自由，机器数据独立。** 不要让机器需求把创作文档变成表单。

## 11. 列表、检索、读取

- `list`：有标题列标题；没有标题用首行/首句。角色卡一人一行，取首行/第一句；卷纲/序列取首行。
- `read`：整篇；有 `section` 按节；正文支持行范围/场景索引。
- `search`：升级成真 grep（正则、上下文、glob、标题、别名）；命中是导航，不直接进上下文。
- 没有固定格，所以没有“第几格”这种地址；地址是路径/小节/行/场景。

- 重复标题不变量（有标题时，标题必须唯一）。

## 13. 新增一种设计文档

1. 在指南注册表加一行：`match`（路径 glob）、`purpose`、`questions`、`examples`、`antiPatterns`、`size`。
2. 不需要新类型、不需要新工具、不需要新白名单。
3. 如果它有机器消费者，先问：消费者要的是**文档内容**还是**独立数据**？后者放账本/元数据，不塞进文档。
4. 在 `docs/` 里写清 purpose 与 questions；不写“必须有哪几格”。

---

## 14. 验收标准

1. 角色卡/卷纲/序列纲没有“缺格即拒”；提案不会因为“没按小节”被拒。
2. 模型读到的是 purpose/questions/examples/antiPatterns，不是模板。
3. 提案审阅是整篇 + diff；局部修改走 `edit`；没有逐格编号。
4. `list`/`read` 不依赖固定字段；标题可选。
5. 机器数据（章型、承诺状态、知识、关系、场景）在独立账本/元数据里。
6. 删除形状不变量后，路径/权限/CAS/原子写仍然生效。
7. 全部用例离线通过；不需要真实模型。

## 附录：开放问题

1. 角色卡的尺寸建议是否要更强？先提示，不硬截断。
2. 卷纲/序列纲的“情绪节奏/体量”是否保留为指南问题？保留为参考，不要求。
3. 设计指南的范例从哪来？先用真实项目里公认好的卡/卷/序列，后续可扩充。
4. 别名索引由卡里的一句话提供，还是单独维护？先允许两者；grep 需要时再统一。
5. 标题可选后，`read section` 对无标题文档退化为整篇/行范围；是否需要自动生成小节索引？先不做。
