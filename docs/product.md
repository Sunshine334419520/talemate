# 产品：talemate 是什么、给谁、不做什么

> **职责**：回答"这个产品为什么存在、为谁解决什么、边界在哪"。
> **读者**：要判断某个功能该不该做的人。
> **对齐代码**：2026-09-19 · 本文不含实现细节，实现看 `architecture.md`
> 相邻：`architecture.md`（怎么做）· `design-docs.md`（写作领域长什么样）· `roadmap.md`（还没做）

## 一句话

**一个让"有想法的人"把小说从念头写到成稿的创作 Agent**——以"活的小说项目空间"为中心，设计段帮你想清楚，写作段帮你写出来，**全程你当主编**。

## 目标用户

主用户是**写手工具**的使用者，两类人：

- **有想法的人**：有故事想法，但写不好、写得慢
- **普通人**：想写出优秀小说，但不知从何下手

MVP 阶段的真实用户画像更窄：**愿意开终端、自带 API key 的写作者/极客**。"普通人"随 UI 阶段进入。

## 核心命题（护城河）

> **能不能让 agent 写出"作者愿意认领"的章节**——把写小说这件高门槛的事，拆成"想清楚 → 写出来 → 人拍板"可协同的流程。

网文行业已经验证了这套工艺知识（代入感/期待感两根柱子、爽点节奏、节拍规划、伏笔回收）。talemate 的做法是**把它们前置到生成时**：

- **设计段**用对话把设定做厚（四层活文档，见 `design-docs.md`）
- **写作段**结构先行——先出节拍，再写正文
- **质量靠上游结构 + 独立上下文分工 + 用户主编拍板**，不靠事后批评循环

## 明确不做的（每条都对应一次否决）

| 不做 | 为什么 |
|---|---|
| **事后打分 / 评判系统 / 编辑循环收敛** | 成本高、收敛慢，且让产品押在"质量可以被检查"这个不可靠前提上。改为**质量前置**：上游结构做对 + 人拍板。 |
| **批评者 / 评审 Agent** | 同上的残留冲动。拍板永远是人。 |
| **导演 / 编排 Agent** | 编排是 editor 的工作协议 + `task` 链，不是一个能对话的角色。 |
| **自动"点子捕捉器" / 后台自动回写企划** | 企划改动走 editor 提议 + 用户拍板，不做事后自动改设想的 agent。 |
| **应用层版本历史** | 版本感靠项目进 git 的 diff，不做应用层版本管理。 |

> 判据：**凡是"让另一个 agent 去审查 agent 产出"的提议，都在重犯评判系统的病。**

## 用户角色贯穿始终

- **设计段**：用户是故事的**主人**（想法是他的），editor 是共创参谋
- **写作段**：用户是**主编**（拍板），Agent 是执行者

姿态从"出想法"变成"做裁决"，角色一直是用户。

## 主流程：以"活的想法"为中心的反馈系统

小说写作第一步是和用户一起**确定想法**，细化后才能规划怎么写，然后才进入正文。**但这不是一次性流水线——想法是"活的锚点"**：初始想法可能只有 50% 完善度，写作依赖它，而写作过程又会浮现新点子，反过来修正它。

```
        ┌────── 写作中浮现的新点子 ──────┐
        ▼                               │
   想法工坊（活的，随时可改、可探讨）◄────┤
        │                               │
        ▼                               │
     规划（随想法更新）──────────────────┤
        │                               │
        ▼                               │
     写作（每次都对着"当前想法"写）──────┘
```

- **想法工坊是常驻能力，不是第一阶段**：任何时候都能回到它
- **写作依赖当前版本**：每次都现读企划，**绝不缓存旧设定**
- **想法生长于写作**：新点子由 editor 在对话中提出、用户拍板后落回企划

### 企划怎么改

- **用户手动为主**：任何时候提出改动，editor 读当前版本、落进对应文档
- **editor 提议为辅**：对话中发现"值得升级的点子 / 前后矛盾"提给用户，拍板后才落盘
- **只影响后续**：已写章节不动，从下一章起按新设定写；回头核查一致性属长篇状态层，后置

## 各阶段工件

| 阶段 | 产出 | 内容 |
|---|---|---|
| **设计段** | **企划 = 分层活文档** | `design/` 四层：core / wiki / characters / outline。初始 ~50% 完善度，持续迭代 |
| **写作段** | **章节细纲 + 正文** | 用户说"写第 N 章" → 先出节拍 → 再写正文 → 落 `chapters/` |
| **用户拍板** | 落盘即确认 | 覆盖设定 / 落盘成品前都要用户看过 |

> **关键区分**：企划是**创作设定的活文档**，从设计段开始积累；**状态层**（连续性日志、伏笔登记、跨章追踪）是长篇独有，后置——见 `roadmap.md`。

## 项目性质与商业模式

| 项 | 决策 |
|---|---|
| 性质 | 商业产品为主（60%），开源倾向（30%），探索学习（10%） |
| 商业模式 | 前期用户**自定义 API key**；验证价值后提供 **token 订阅制** |
| 形态 | **完全独立的软件**，借鉴 OpenCode / Claude Code 的架构模式（不是依赖、不是插件生态） |
| 第一版形态 | CLI 先行，UI 后置——**写不出好文章，UI 无用** |

## 演进方向

1. **UI 阶段**：Web/桌面工作台（大纲、人设、章节、审阅按钮），"普通人"进入
2. **上传提取文风**：3-5 篇样本 → 提取 agent → 结构化风格规范
3. **状态层 / 长篇**：连续性日志、伏笔登记、跨会话记忆——换作品结构 + 加状态层，写作引擎不动
4. **token 订阅制**
