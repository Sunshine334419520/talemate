# 知识点 13 · 「好」的四个维度

> **职责**：把手册 §3.1 讲透——为什么「这个 prompt 更好」必须先说清是哪个维度、愿意付什么代价；四个维度各自怎么测、在 talemate 里长什么样。
> **读者**：准备进入第 3 章、但还习惯用「感觉更好」评价 prompt 的我。
> **对齐代码**：不涉及代码 · 对齐手册 §3.1 / §3.4 / §3.6（2026-10-30 版）

---

## 一分钟版

> 「好」不是一个数，是**四个维度上的位置**：能力上限、可靠性、经济性、可维护性。  
> 判断之前先声明：这次主要改哪个维度、哪些维度不能退、愿意付多少成本。  
> 否则两个人会拿不同的数吵同一件事——一个说「通过率涨了」，一个说「贵了一倍、还更难维护」。

---

## 1. 为什么不能只说「这个 prompt 更好」

同一份 prompt 改动，可能同时：

- 让模型偶尔写出惊艳的段落（能力上限↑）
- 但三次里有两次跑偏（可靠性↓）
- 每次多花 40% token（经济性↓）
- 把同一条规则抄进三个文件（可维护性↓）

如果只说「更好」，你其实只报了其中一个维度，另外三个被静默忽略。  
所以第 3 章的第一条纪律不是「怎么打分」，是：

> **先声明在哪个维度、愿意付什么代价。**

这句话不是礼貌，是判据的一部分。没有它，后面的 rubric、judge、统计都无处落脚。

---

## 2. 四个维度

| 维度 | 问题 | 典型指标 | 可接受的代价 |
|---|---|---|---|
| **能力上限** | 它能不能做对？ | pass@k（k 次里有 1 次对） | 可以贵、可以慢 |
| **可靠性** | 它是否稳定做对？ | pass^k（k 次全对）、方差 | 必须稳，宁可慢 |
| **经济性** | 做对要多少钱？ | token/任务、成本 delta、P50/P95 延迟 | 可以略贵，不能翻倍 |
| **可维护性** | 改动会不会污染别处？ | diff 大小、载体归属、耦合面 | 不能留下隐式依赖 |

四个维度不是「四个评分项」，是**四个不同的产品问题**。  
一个 prompt 可以在 A 上变好、在 B 上变坏；不声明维度，就没有「更好」这回事。

---

## 3. 能力上限：它到底能不能做对

### 3.1 问法

> 给足够多次机会，它有没有一次能做对？

对应 **pass@k**：k 次里至少一次通过。

### 3.2 它适合回答什么

- 这个任务模型有没有可能完成？
- 这个 prompt 是否提供了完成任务所需的信息？
- 换一个更强的模型，上限会不会更高？

### 3.3 它不能回答什么

- 用户每次都能拿到好结果吗？
- 第十章会不会突然崩？
- 这次改动值不值得上线？

**能力上限高，不等于产品可用。**  
一个 10% 概率写出神作的 prompt，pass@3 可能不错，但 pass^3 很差；产品要的是后者。

### 3.4 talemate 例子

「让模型写出古言腔」：

- 能力上限：给它 3 次，至少一次像古言；
- 但这不代表每章都像古言。

如果只看一次惊艳样本就保留 prompt，等于拿 pass@1 的运气当可靠性。

---

## 4. 可靠性：它是否稳定做对

### 4.1 问法

> 同一配置重复跑，多少次能全对？

对应 **pass^k**：k 次全部通过，以及方差/失败率。

### 4.2 为什么产品更看重它

talemate 写一章正文：

- 写坏一章的代价：用户要重读、重写、失去信任；
- 多花两分钱的代价：几乎可以忽略。

所以正文场景通常**可靠性优先**：pass^3 比 pass@3 更该作为主指标。  
这不是「能力不重要」，是「能力已经够用时，稳定性决定产品体验」。

### 4.3 可靠性不是「跑很多次取平均」

平均分高但方差大，意味着：

- 有些用户每次都遇到坏结果；
- 你无法预测下一次；
- 回归时容易被平均值掩盖。

所以可靠性要看：

- pass^k；
- 方差；
- 失败桶分布；
- 最差 case 是否稳定坏。

### 4.4 例子

Prompt A：

```text
pass@3 = 80%（三次里至少一次好）
pass^3 = 30%（三次全好）
```

Prompt B：

```text
pass@3 = 70%
pass^3 = 60%
```

产品该选哪个？  
如果用户只写一次，A 的「至少一次」没有意义；B 更可能每次都交付。  
这就是为什么「能力上限」和「可靠性」要分开报。

---

## 5. 经济性：做对要多少钱

### 5.1 问法

> 做对一次，平均花多少 token、多少钱、多少时间？

指标：

- token/任务；
- 成本 delta；
- P50 / P95 延迟；
- 重试次数；
- 失败后的返工成本。

### 5.2 不能只看「成功那一次」的成本

一个 prompt 可能：

- 成功时很便宜；
- 但失败率高，重试三次才成功；
- 总成本反而更高。

所以经济性要把**失败与重试**算进去，不是只看成功样本的 token。

### 5.3 可接受的代价

手册给的边界是「可以略贵，不能翻倍」。  
具体阈值要在预注册里写死，例如：

```text
成本 delta ≤ +20%
P50 延迟 ≤ +30%
```

超过就是「不保留」，即使质量涨了。  
这不是抠门，是产品约束：一个每次多花一倍成本的 prompt，无法长期跑。

### 5.4 talemate 例子

给 prompt 加 2000 字风格范例：

- 可能提升能力上限；
- 但每轮多 2000 token，且每次请求都付；
- 如果风格范例应该放 skill 卡、按需加载，就不该常驻 prompt。

这就是经济性和可维护性的交叉点。

---

## 6. 可维护性：改动会不会污染别处

### 6.1 问法

> 这条规则应该放在哪？改了它，会不会让另一个模式/角色/文档跟着变？

指标不是只有 diff 大小，还包括：

- **载体归属**：persona / mode / tool / skill / design，哪一层拥有这条规则？
- **重复**：同一条规则是否抄进了多个文件？
- **耦合**：改 A 是否迫使 B 也改？
- **可推导性**：这份清单能不能从代码/注册表推导，而不是手抄？
- **可回滚性**：出问题时能不能只撤这一处？

### 6.2 为什么它是一等公民

一个 prompt 可能今天让分数涨了，但：

- 把角色名硬编码进 persona；
- 把只在 draft 模式成立的规则写进全局；
- 把同一句话复制到三个 agent 的 system；
- 让下一个改 prompt 的人不知道哪份才是真的。

这类改动会让后续每次实验都变贵——**你省下的是这一次的 token，付出的是之后每次维护的成本。**

### 6.3 talemate 例子

「用户没确认前不要写 characters/」这条规则：

- 应该放在 **draft 模式**，不是全局 persona；
- 因为只在 draft 阶段成立；
- 放进全局会污染 mate/prose 模式；
- 复制到三个地方会产生漂移。

可维护性好的改动，通常：

- 只改一个载体；
- 规则只出现一次；
- 其他文件引用它，而不是复述它。

## 7. 四个维度怎么一起用

### 7.1 先选「主维度」，再定「护栏」

不要四个都当主指标。一次改动选一个：

```text
主维度：可靠性（pass^3）
护栏 1：能力上限不显著下降（pass@3）
护栏 2：成本 delta ≤ +20%
护栏 3：不新增重复规则 / 不硬编码
```

主维度决定「这次成不成」，护栏决定「不能为了它把别的搞坏」。

### 7.2 四维不是加权求和

不要做：

```text
总分 = 0.4 * 能力 + 0.3 * 可靠性 + 0.2 * 经济 + 0.1 * 可维护
```

原因：

- 权重是拍脑袋的；
- 不同维度的单位不同；
- 加权会把「安全回退」这种硬约束稀释成一个可接受的小数。

正确做法是**向量 + 约束**：

```text
(能力, 可靠性, 成本, 可维护性)
必须满足：可靠性 ≥ baseline，成本 ≤ +20%，无重复规则
```

### 7.3 预注册模板

```text
【预注册】<改动名>

主维度：可靠性（pass^3）
假设：<改什么> 会让 pass^3 从 X 到 Y，同时不破坏以下护栏。

护栏：
  1. 能力上限：pass@3 不显著下降
  2. 经济性：成本 delta ≤ +20%，P50 延迟 ≤ +30%
  3. 可维护性：不新增重复规则、不硬编码具体作品内容
  4. 安全：越权写盘 = 0

通过条件：主维度净翻转 ≥ 6/30，McNemar p < 0.05，留出集同向，护栏全过。
失败处置：回滚；失败样本进回归集；结论进 ADR。
```

## 8. 一个完整的对比例子

假设两个 prompt 变体：

| | A（加长版） | B（结构化版） |
|---|---|---|
| 能力上限 pass@3 | 82% | 78% |
| 可靠性 pass^3 | 38% | 61% |
| 成本 delta | +65% | +12% |
| 可维护性 | 规则抄进 3 个文件 | 只改 draft 模式一处 |

如果产品是「每章都要稳定交付」：

- A 的能力上限略高，但可靠性差、成本高、维护差；
- B 的能力上限略低，但可靠性、经济性、可维护性都更好；
- 主维度是可靠性 → **B 更可能是正确选择**。

如果产品是「偶尔生成一个惊艳开头，用户会自己挑」：

- A 可能更合适，因为能力上限优先，失败可接受。

**同一个 prompt，在不同产品目标下可以有不同的「好」。**  
这就是为什么必须先声明维度，而不是先争「哪个分数高」。

## 9. 常见误解

| 误解 | 为什么错 |
|---|---|
| 「分数涨了就是更好」 | 只报了一个维度；成本、可靠性、可维护性可能同时变坏 |
| 「更长、更详细 = 更好」 | 常在经济性和可维护性上付出代价；细节要放在对的载体 |
| 「pass@3 高就代表稳定」 | pass@3 是能力上限，pass^3 才是可靠性 |
| 「平均分高就行」 | 平均值会掩盖方差和最差 case；产品可能每次遇到坏结果 |
| 「可维护性是软指标，不用管」 | 重复规则会漂移，硬编码会阻止下一次实验；它是长期成本 |
| 「四个维度加权成一个总分」 | 单位不同、权重拍脑袋，还会稀释安全护栏 |
| 「先跑分，之后再想维度」 | 事后选维度 = 事后找理由；预注册必须在看数字之前 |

## 10. 自检

1. 一个 prompt 把 pass@3 从 70% 提到 85%，但 pass^3 从 55% 降到 35%，成本 +40%。  
   哪个维度变好、哪个变坏？如果产品是「每章稳定交付」，该保留吗？
2. 为什么「更长、更详细」不天然更好？至少从经济性和可维护性各说一条。
3. 「用户没确认前不要写 characters/」这条规则应该放在哪一层？为什么不应复制进三个 agent 的 system？
4. 写一个预注册：主维度、两个护栏、一个失败处置。不要写「感觉更好」。
5. 为什么不能把四个维度加权成一个总分？说出两个理由。
