# 章节生产：目标架构

> **职责**：定下"写一章"这条流水线的目标架构——谁规划、谁批准、谁执行、工件放哪、哪些现有断言要被推翻。
> **读者**：要动手改这条流水线的人；以及想知道"为什么不是 writer 子代理了"的人。
> **对齐代码**：**尚未落地**（2026-09-24 定稿）。本文描述的是**目标**，现状见 `design-docs.md`「写作段」与 `agents.md` 的角色名册——两处状态不一致时，以代码为准。
> 相邻：`product.md`（为什么这么做）· `design-docs.md`（现状）· `agents.md`（角色与工具）· `outline.md`（序列纲与章计划）· `roadmap.md`（落地后要删的条目）

## 一、为什么要改

四条动机，每条都有出处，不是口味问题。

**① 正文写作不满足 SubAgent 的判据。** SubAgent 买的是"中间材料不进主线，**你只要结论**"。而正文**没有比它更短的结论**——产物就是全部中间材料。对比查证：读 20 个页面回来一句结论，那是判据的教科书案例；正文不是。

**② 正文必须进 mate 的上下文。** `product.md` 写着「**想法生长于写作**：新点子由 mate 在对话中提出、用户拍板后落回企划」。**mate 没见过正文，就识别不出写作中浮现的新点子。** 现在的设计（writer 写、mate 只拿摘要）与这条自相矛盾。

**③ 章末回写被 writer 子会话挡着。** `roadmap.md` 的「状态层」已经记下这个坑：*章节在 writer 子会话里落盘，`write` 的结果到不了 mate，唯一到得了的是 `<task_result>`*。mate 自己写正文，这个坑自动消失——`write` 的结果直接回到 mate。

**④ 局部修改没有出路。** 用户要改某一段正文时：走 writer 会被"一次批准 = 一次写作"的门挡住（`core_tools.ts` 查 `PLAN_KEY.approved`，`task(writer)` 成功后即清）；走 mate 的 `edit` 又没有文风纪律（那几条只写在 `writer.system.txt` 里）。两头都堵。

另外还有一条产品层面的收益：**mate 自己写，正文是流式打在用户眼前的**。现在 writer 的正文在 `write` 弹确认之前完全不可见，用户最后只看到一份 diff——而 `mate.system.txt` 第一句写的是 "you do the work **in front of them**"。

## 二、目标架构

```
用户："写第 3 章"
   │
   ▼
mate ──task(规划者)──► 规划者（独立上下文）
   │                     读设定 · 查资料 · 起草节拍与人物
   │◄──── 一份可执行规划
   │
   ├─ 落 <novel>/.talemate/plans/ch_3.md
   ├─ 摆给用户 ──► 接受 → 执行 ／ 不接受 → 改（再摆一次）
   │
   ▼ 接受
mate 执行：skill(prose) 加载文风 → 自己写正文 → 写后步骤（状态，见「未决」）

随时可用：
  世界观 / 角色 / 大纲设计时，mate 任何时候都能派 researcher 查一个事实
```

**四个东西**：

| | 是谁 | 干什么 |
|---|---|---|
| **规划者** | SubAgent | 一个章节意图 → 一份**可执行规划** |
| **researcher** | SubAgent | 跨阶段的**查证**：世界观、角色、大纲、章节规划都用得到它 |
| **mate** | primary | 执行规划：写正文（加载文风 skill）、写状态 |
| **用户** | — | 批准者。mate 摆出规划 → 接受就执行，不接受就改 |
| **工作区** | — | `<novel>/.talemate/plans/` 放规划工件 |

**规划者与 researcher 不重叠**：阶段不同（章节级 vs 任意时刻）、粒度不同（一份工作单 vs 一个事实）、产出不同。

## 三、规划是什么

**一串"要落地的产物"，不是自由文本。**

为什么这么定：如果"第一步做完了没有"由模型自述，就不可靠——本仓已有先例（提案的 `approved` 由 harness 按用户回话置位，**模型自述无效**）。所以每一步声明**它要产出什么**，产物存在即完成。

```markdown
# 第 3 章规划                    ← <novel>/.talemate/plans/ch_3.md

意图：<用户这一章要什么>

产物（按序）：
  1. chapters/chapter_ch3_v1.md      ← 正文
  2. <状态回写的目标>                 ← 形状待定，见「未决」

第 1 步要什么：
  节拍：<...>
  需要的角色：<...>（各自要立住的点）
  查证结论：<...>（带出处）

第 2 步要什么：
  谁变了、从什么变成什么
```

**规划落在 `.talemate/plans/`，不进 `design/`。** 边界是：`design/` + `chapters/` 是**作品**（用户的、要被审阅的、可进版本控制的）；`.talemate/` 是**引擎的工作区**（可清理、用户不必看、不参与 `list` / `search` / 不变量 / 规范）。规划是"这一次执行"的状态，不是作品的一份文档。

## 四、决定的边界

同样的机制，来源不同——左边是场景本身要求的，右边只是现有实现的习惯。改的时候只该动右边。

| 机制 | 来源 |
|---|---|
| **"待批准态 + mate 在此停手"** | **场景要求**：用户要能"接受/不接受"，就必须有一个"摆出来了但还没执行"的状态 |
| **用户回话被解释为裁决** | **场景要求**：靠"有一份待批准的东西"，**不靠模式**（`session.ts` 的 `markPendingApproval` 只看 pending） |
| **评审期间冻结**（不让 mate 同时改别的） | **场景要求，但只在文档提案那条路上**。规划是引擎状态，冻结对它无意义 |
| 草稿模式作为**规划**的前置 | 现有习惯 → **扔** |
| `propose-plan` 的"节拍"定位 | 现有习惯 → 语义换成"提交规划" |
| `design/outline/plan_ch<N>.md` 这个路径 | 现有习惯，**而且错了** → **扔**（规划归 `.talemate/`） |
| "一次批准 = 一次写作" | 现有习惯 → 换成"一次批准 = 一份规划" |

## 五、本文落地后会推翻的断言

| 现有说法 | 位置 | 处置 |
|---|---|---|
| 节拍**不落盘** | `design-docs.md` 写作段 | 推翻——规划落 `.talemate/plans/` |
| `propose-design` 的合法目标含 `design/outline/plan_ch<N>.md` | `prompts/tools/propose-design.txt` + `design_spec.ts` | 删掉该目标 |
| 规划要先 `enter-draft` | `prompts/tools/propose-plan.txt` + `core_tools.ts` 的模式守卫 | 推翻——草稿模式只服务文档提案 |
| 一次批准 = 一次写作 | `core_tools.ts` | 推翻 |
| 正文由 `task(writer)` 写 | `agents.md` 名册 + `mate.system.txt` + `writer.system.txt` | 推翻——mate 写，加载文风 skill |
| `product.md` 的"独立上下文分工"用在正文 | `product.md` | 挪到章节规划阶段 |
| `roadmap.md` 的「正文由谁落盘」「状态层·章末回写」 | `roadmap.md` | 落地后删（那条「折中落点（未采纳）：writer 落盘 + 短摘要」随问题一起作废） |

**保留不动**：`design-docs.md` 的「mate 没有阶段状态机」。它说的是**对话阶段**（设计段/写作段由用户点名驱动），而规划里的步骤是**一份工件的内容**——两者不是一回事。

## 六、落地要动的东西

1. **`.talemate/plans/`** —— 新目录 + 清理策略。`src/core/config.ts` 加路径；清理**今天不存在**（`sessions/` 也是只增不减），所以这是要建的，不是已有的。
2. **内置 skill 库** —— 仓库根 `skills/`，在 `src/skill/discovery.ts` 里作为**最低优先级**扫描根（用户全局库、项目库可同名覆盖）。`roadmap.md` 的 P2「文风卡迁移成 skill 库」说的就是它；P3 的 `style-extractor` 是它未来的生产者。
3. **`skills/prose/`** —— 文风纪律从 `writer.system.txt` 搬到这里（单一来源），mate 写正文前 `skill prose` 加载。
4. **规划者 SubAgent** —— 带 `read` 与网络工具。**注意深度上限是 1**，它不能再派 researcher，要自己查。
5. **提交规划的工具** —— 语义从"节拍"换成"规划"；去掉草稿模式前置；批准粒度从"一次写作"改成"一份规划"。
6. **mate 侧** —— `mate.system.txt` 的「绝不自己写正文」改成「正文由你自己写，先加载文风」；规划摆出与裁决复用现成的 pending 机制。
7. **`writer` 角色** —— 删除（或改造）。它存在的理由（隔离正文）在新架构下不成立。

## 七、未决

**状态层**（规划里的"写后步骤"）。`design/state/` 尚未落地，连规范都没有——本文只**预留一个步骤位**，形状等那块做的时候再定。`roadmap.md` 的「状态层」条目继续有效。

## 八、明确不为它造机制的事

**执行中发现更好的走法**：就地按新的写。

规划是**写作前**的准备，管不到写作中的发现；写完才发现的问题更是如此——那就是一次局部修改，**直接在主 Agent 里做**，不需要"变更申请"、不需要追加提案、不需要任何仪式。给这件事造机制，等于把"继续干活"错当成"变更申请"。
