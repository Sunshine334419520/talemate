# 章节生产：谁规划、谁批准、谁执行

> **职责**：定下"写一章"这条流水线的架构——谁规划、谁批准、谁执行、工件放哪；并记下它推翻了哪些旧断言、为什么。
> **读者**：要动手改这条流水线的人；以及想知道"为什么不是 writer 子代理了"的人。
> **对齐代码**：**已落地**（2026-09-28）· 工件在 `framework/plan.ts`，门在 `tool/core_tools.ts` 的 `propose-plan`，角色在 `agent/registry.ts`。本文与代码冲突时以代码为准。
> 相邻：`product.md`（为什么这么做）· `design-docs.md`（设计文档体系与章节生产那条链）· `agents.md`（角色与工具）· `outline.md`（序列纲与章规划）· `roadmap.md`（状态层还没做）

## 一、为什么要改

四条动机，每条都有出处，不是口味问题。

**① 正文写作不满足 SubAgent 的判据。** SubAgent 买的是"中间材料不进主线，**你只要结论**"。而正文**没有比它更短的结论**——产物就是全部中间材料。对比查证：读 20 个页面回来一句结论，那是判据的教科书案例；正文不是。

**② 正文必须进 mate 的上下文。** `product.md` 写着「**想法生长于写作**：新点子由 mate 在对话中提出、用户拍板后落回企划」。**mate 没见过正文，就识别不出写作中浮现的新点子。** 现在的设计（writer 写、mate 只拿摘要）与这条自相矛盾。

**③ 章末回写被 writer 子会话挡着。** `roadmap.md` 的「状态层」已经记下这个坑：*章节在 writer 子会话里落盘，`write` 的结果到不了 mate，唯一到得了的是 `<task_result>`*。mate 自己写正文，这个坑自动消失——`write` 的结果直接回到 mate。

**④ 局部修改没有出路。** 用户要改某一段正文时：走 writer 会被"一次批准 = 一次写作"的门挡住（`core_tools.ts` 查 `PLAN_KEY.approved`，`task(writer)` 成功后即清）；走 mate 的 `edit` 又没有文风纪律（那几条只写在 `writer.system.txt` 里）。两头都堵。

另外还有一条产品层面的收益：**mate 自己写，正文是流式打在用户眼前的**。现在 writer 的正文在 `write` 弹确认之前完全不可见，用户最后只看到一份 diff——而 `mate.system.txt` 第一句写的是 "you do the work **in front of them**"。

## 二、目标架构

```
用户："写第 3 章"
   │
   ▼
mate ──task(规划者)──► 规划者（独立上下文）
   │                     读设定 · 查资料 · 起草节拍与人物
   │◄──── 一份可执行规划
   │
   ├─ 落 <novel>/.talemate/plans/ch_3.md
   ├─ 摆给用户 ──► 接受 → 执行 ／ 不接受 → 改（再摆一次）
   │
   ▼ 接受
mate 执行：harness 随 system 注入正文规范 + 文风卡 → 自己写正文 → 写后步骤（状态）

随时可用：
  世界观 / 角色 / 大纲设计时，mate 任何时候都能派 researcher 查一个事实
```

**四个东西**：

| | 是谁 | 干什么 |
|---|---|---|
| **规划者** | SubAgent | 一个章节意图 → 一份**可执行规划** |
| **researcher** | SubAgent | 跨阶段的**查证**：世界观、角色、大纲、章节规划都用得到它 |
| **mate** | primary | 执行规划：写正文（规范与文风由 harness 注入）、写状态 |
| **用户** | — | 批准者。mate 摆出规划 → 接受就执行，不接受就改 |
| **工作区** | — | `<novel>/.talemate/plans/` 放规划工件 |

**规划者与 researcher 不重叠**：阶段不同（章节级 vs 任意时刻）、粒度不同（一份工作单 vs 一个事实）、产出不同。

## 三、规划是什么

**一串"要落地的产物"，不是自由文本。**

为什么这么定：如果"第一步做完了没有"由模型自述，就不可靠——本仓已有先例（提案的 `approved` 由 harness 按用户回话置位，**模型自述无效**）。所以每一步声明**它要产出什么**，产物存在即完成。

```markdown
# 第 3 章规划                    ← <novel>/.talemate/plans/ch_3.md

意图：<用户这一章要什么>

产物（按序）：
  1. chapters/chapter_ch3_v1.md      ← 正文
  2. <状态回写的目标>                 ← 形状待定，见「未决」

第 1 步要什么：
  节拍：<...>
  需要的角色：<...>（各自要立住的点）
  查证结论：<...>（带出处）
  放大点：<哪一刻慢镜头几百字、哪些半句带过>（每一步都要有——全章一个力度是平庸最常见的走法）

第 2 步要什么：
  谁变了、从什么变成什么
```

**规划落在 `.talemate/plans/`，不进 `design/`。** 边界是：`design/` + `chapters/` 是**作品**（用户的、要被审阅的、可进版本控制的）；`.talemate/` 是**引擎的工作区**（可清理、用户不必看、不参与 `list` / `search` / 不变量 / 规范）。规划是"这一次执行"的状态，不是作品的一份文档。

**三条落实时的具体决定**（`framework/plan.ts`）：

- **谁写这个文件**：`propose-plan` 工具自己写。`write` 只认作品的三个根（`design/` / `chapters/` / `state/`），而规划按上面的边界不归其中任何一个；它也不该走 `write_ops` 那条作品文档的路（diff、CAS、权限 pattern 一样都不需要）——整篇写、整篇渲染给用户看，**用户看过的字节就是落盘的字节**。
- **按章命名**：`ch_<N>.md`，N 是章号（`propose-plan` 的 `chapter` 参数就是这个数，不是展示用的字符串）。一章一个文件 → **同一章再交一份即覆盖**，这就是清理策略：数量由章数封顶，不需要按时间或次数删。执行完**不删**——它是那一次执行的记录。
- **`read` / `list` 读不到它**（那是 `.talemate/` 的边界，不是漏做）。所以 `renderPendingNote` 每轮把**路径报出来**，mate 在压缩之后仍知道它存下来了。

**代码不校验规划的形状**（不认识"产物"那一节）。判据是"**字节能不能到用户眼前**"：规划整篇摆给用户看，一份没写产物的规划他当场看得见。`propose-design` 那道的 `reviewable` 之所以存在，是因为**提案会渲染成一页空白却照样落盘**——那种失败模式在这里不存在。

## 四、决定的边界

同样的机制，来源不同——左边是场景本身要求的，右边只是现有实现的习惯。改的时候只该动右边。

| 机制 | 来源 |
|---|---|
| **"待批准态 + mate 在此停手"** | **场景要求**：用户要能"接受/不接受"，就必须有一个"摆出来了但还没执行"的状态 |
| **用户回话被解释为裁决** | **场景要求**：靠"有一份待批准的东西"，**不靠模式**（`session.ts` 的 `markPendingApproval` 只看 pending） |
| **评审期间冻结**（不让 mate 同时改别的） | **场景要求，但只在文档提案那条路上**。规划是引擎状态，冻结对它无意义 |
| 草稿模式作为**规划**的前置 | 现有习惯 → **扔** |
| `propose-plan` 的"节拍"定位 | 现有习惯 → 语义换成"提交规划" |
| `design/outline/plan_ch<N>.md` 这个路径 | 现有习惯，**而且错了** → **扔**（规划归 `.talemate/`） |
| "一次批准 = 一次写作" | 现有习惯 → 换成"一次批准 = 一份规划" |

## 五、落地时推翻的断言

这张表是**改动清单**：读这份文档的人多半记得旧设计，这里说清每一处旧说法现在是什么。

| 旧说法 | 位置 | 处置 |
|---|---|---|
| 节拍**不落盘** | `design-docs.md` 写作段 | **推翻**——规划落 `.talemate/plans/ch_<N>.md` |
| `propose-design` 的合法目标含 `design/outline/plan_ch<N>.md` | `prompts/tools/propose-design.txt` + `design_tools.ts` 的入参描述 | **删掉**该目标 |
| 规划要先 `enter-draft` | `prompts/tools/propose-plan.txt` + `core_tools.ts` 的模式守卫 | **推翻**——草稿模式只服务文档提案 |
| 一次批准 = 一次写作 | `core_tools.ts` 的 `task` 硬门与"用掉即清" | **推翻**——门只剩 `propose-plan` 的 `halt` |
| 正文由 `task(writer)` 写 | `agents.md` 名册 + `mate.system.txt` + `writer.system.txt` | **推翻**——`writer` 与 `writer.system.txt` 已删，mate 那条禁令随之**取消**（不是翻转）；正文由 mate 自己写；规范在 `prompts/prose.rules.txt`、文风卡在 `skills/`，由 harness 在写作窗口注入 |
| `product.md` 的"独立上下文分工"用在正文 | `product.md` | **挪到**章节规划阶段 |
| `roadmap.md` 的「正文由谁落盘」「状态层·章末回写」 | `roadmap.md` | **已删**（回写的障碍随 writer 一起消失，理由并进「状态层」那一节） |

**保留不动**：`design-docs.md` 的「mate 没有阶段状态机」。它说的是**对话阶段**（设计段/写作段由用户点名驱动），而规划里的步骤是**一份工件的内容**——两者不是一回事。

## 六、落地动了什么

1. **`.talemate/plans/`** —— 新目录 + 清理策略（`src/core/config.ts` 的 `projectPaths.plans` + `framework/plan.ts`；清理策略见「三」末尾）。
2. **内置 skill 库** —— 仓库根 `skills/`，在 `src/skill/discovery.ts` 里作为**最低优先级**扫描根（用户全局库、项目库可同名覆盖）。`roadmap.md` 的 P2「文风卡迁移成 skill 库」说的就是它；P3 的 `style-extractor` 是它未来的生产者。
3. **`skills/prose/` + `prompts/prose.rules.txt`** —— 文风纪律从 `writer.system.txt` 搬出来，**并拆成两层**：可判对错的跨文风规矩归**规范**（`prompts/`），"像不像这个声音"归**文风卡**（`skills/` 库，默认那张是 `prose`）。两层由 harness 在写作窗口拼起来注入，理由见 `agents.md` 的 Skill 系统那条例外与 `framework/prose.ts`。
4. **规划者 SubAgent** —— 带 `read` 与网络工具。**注意深度上限是 1**，它不能再派 researcher，要自己查。
5. **提交规划的工具** —— 语义从"节拍"换成"规划"；去掉草稿模式前置；批准粒度从"一次写作"改成"一份规划"。
6. **mate 侧** —— `mate.system.txt` 那条「绝不自己写正文」**删掉，不是改成它的反面**。writer 一没，它就挡不住任何东西了（剩下两个子代理都是类别拒的只读），而"什么时候派谁"的契约本来就在 `task` 的目录里——`planner` 的 description 写着 "Not for prose"。**留下一句同义反复的禁令，只会让下一个人以为还有个 writer 要防。** 规划摆出与裁决复用现成的 pending 机制。
7. **`writer` 角色** —— 删除（或改造）。它存在的理由（隔离正文）在新架构下不成立。

## 七、状态层（原「未决」，已落地）

那个预留的步骤位填上了：规划里的"写后步骤"就是**状态回写**——每章落盘之后，把变化写回 `state/`
（角色的处境、伏笔账、这一章的流水）。判据、形状与三条纪律见 `state.md`。

当时的两条顾虑都已作罢：

- **"契约挂在哪个工具的结果上"**：从前卡在这里——章节在 writer 子会话里落盘，`write` 的结果到不了 mate。mate 自己写正文之后，`write` 的结果直接回到它手里。
- **"形状待定"**：定下来的形状是**不定义形状**——`state/` 下的文件自由内容、工具不校验；加一类状态是建一个目录，不是加一个类型。

序列进度那一环也清楚了：**报位置（读到第几章），不报剩余**——"还剩几件功能没兑现"由规划者现读现判，因为序列纲声明的是功能不是可勾的清单。见 `outline.md` 与 `roadmap.md`。

## 八、明确不为它造机制的事

**执行中发现更好的走法**：就地按新的写。

规划是**写作前**的准备，管不到写作中的发现；写完才发现的问题更是如此——那就是一次局部修改，**直接在主 Agent 里做**，不需要"变更申请"、不需要追加提案、不需要任何仪式。给这件事造机制，等于把"继续干活"错当成"变更申请"。
