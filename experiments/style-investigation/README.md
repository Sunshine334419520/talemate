# 第一章文风问题排查

对象：

- 产品生成：`~/.talemate/novels/novel-a556/chapters/chapter_ch1_v1.md`
- 文风台样本：[06-guyan--s1.md](../style-bench/outputs/guyan-deepseek/guyan-base/06-guyan--s1.md)

先给结论：**这两篇不是同一个场景，不能直接得出“文风卡失效”的结论。** 但它们暴露了三个可以单独验证的差异：场景/计划、产品 system 栈、生成方式（工具调用 + 长历史）。

## 1. 量化差异

两篇都经过 `formatProse`（一句一段），所以段落数量不是排版造成的，是句子本身的长短。

| | 文风台 | 产品第一章 |
|---|---:|---:|
| 正文字符 | 4,565 | 4,620 |
| 段落数 | 86 | 206 |
| 平均段长 | 53.1 字 | 22.4 字 |
| 句子数 | 103 | 211 |
| 平均句长 | 44.3 字 | 21.9 字 |
| 对话开头段落占比 | 4.7% | 6.3% |

产品稿不是“没有对话”，而是**句子被切得很短、段落很碎**。文风卡明确写“中长句为主”，产品稿没有做到。

## 2. 产品生成时实际给了什么

我把当时的 system 重建出来了：

- [product system（8,135 字）](prompts/chapter1-system.txt)
- [文风台 system（2,638 字）](prompts/bench-guyan-system.txt)
- [第一章计划（4,667 字）](prompts/chapter1-plan.md)

实际请求的规模（按当时的会话）：

| 项 | 产品 | 文风台 |
|---|---:|---:|
| system | 8,135 字 | 2,638 字 |
| 工具 schema | 18 个 | 0 |
| 送进模型的历史消息 | 163 条（79 条会话消息展开） | 0 条（只有一条 user） |
| 最近一次 input | 约 63,942 tokens | 约几千 tokens |

### 产品 system 的顺序

1. `prompts/mate.system.txt`（1,840 字节）
2. `【常驻设定 · design/core.md】`（943 字节，全文）
3. `【常驻设定 · design/wiki/world.md】`（2,861 字节，全文）
4. `<pending-proposal>`：已批准的规划，要求按产物顺序执行
5. `<prose-window>`：
   - `prompts/prose.rules.txt`（六条底线）
   - 完整 `skills/style-02-guyan/SKILL.md`（6,109 字节）
   - 输出路径
6. 18 个工具 schema

### 文风台 system 的顺序

1. “你在写中文网络小说的正文。只输出正文，不要标题、提纲、说明、评价、前言后语。”
2. 六条底线（`rules/relaxed.txt`）
3. 同一张 `style-02-guyan` 卡
4. 一层 user：用例 06

**文风台和产品用的是同一张卡、同一套底线。** 差别只在“卡外面包着什么”。

## 3. 几个明显的冲突/干扰

### A. 场景本身不同

文风台用例是“寿宴前退婚局”：一屋子人、当面交锋、话里有话。产品第一章的计划写的是：

> 不给爽感，不给反抗，只给她“看清”。

计划里的场景是醒来、辨年岁、极简及笄、听国丧、被母亲挡话。它天然更静、更内省。拿“退婚局”的密度要求“及笄日”的开篇，本身就不公平。

**这是第一优先要排除的变量。** 先用同一个计划/同一个场景跑文风台，才能判断是卡的问题还是场景的问题。

### B. `mate.system` 的“plainly and directly”

产品 system 第一段是搭档人格，曾有一句：

> Output goes to a command line. Write in Chinese, plainly and directly.

文风卡说“中长句为主、四字词、俗语、反问、情绪要足”。这两条在打架。文风台没有这句“plainly and directly”。

**这一句已经从 `prompts/mate.system.txt` 移除。** 只移除了这句聊天语气，保留“Stop when you are done / emoji”等其它对话规则。C1 实验显示单删这一句没有把句子拉长（20.2 字/句），所以它不是主因；但既然它是直接冲突项，先去掉再继续。

### C. 常驻全文设定 + 18 个工具 + 163 条历史

文风台没有 core/world、没有工具、没有历史。产品把“写作不得违背”的世界观全文、已有工具调用、前 79 条对话一起塞给模型。模型可能优先做“合规的助手”，而不是“讲故事的叙述者”。

### D. 生成方式不同

文风台是纯文本补全；产品是通过 `write` 工具生成 `content` 参数。模型在工具调用模式里更容易写短、写“像参数”，而不是写长段叙述。这是一条独立变量。

### E. 模型/温度不同

文风台 manifest 是 `deepseek-v4-flash`，temperature `0.8`；产品会话是 `deepseek-flash`，没有显式 temperature。先确认两者是否同一模型、同一采样参数。

### F. 执行指令

第一章那次生成前，接受规划后的内部指令是命令式的（“开始写正文”）。命令式指令 + 工具调用 + 长上下文，会强化“赶紧完成”的姿态，而不是“进入声音”。这条现在已经改成“按产物顺序执行”，但生成这一稿时可能还是旧指令。

## 4. 实验方案

控制变量：同一模型、同一 temperature、同一采样数；先 1 篇筛选，再 3 篇盲评。每篇都过 `formatProse`，都量平均句长、平均段长、对话占比。

### Phase 0：确认文风台可复现

用同一个模型/温度重跑 `guyan-base` + `06-guyan`，确认不是模型版本漂移。

### Phase 1：同场景

| 组 | system | 输入 | 回答 |
|---|---|---|---|
| A | 文风台 | 06-guyan | 基线 |
| B | 文风台 | 第一章计划 | 场景/计划是不是主因 |
| C | 产品全文 system | 第一章计划 | 产品栈是不是主因 |
| D | 产品全文 system | 06-guyan | 同一场景下产品栈的差异 |

**如果 B 明显比 A 短、比 A 平，先修计划/场景，不要先改文风卡。**
**如果 B 好、C 差，问题在产品 system 栈。**

### Phase 2：逐项消融（都用第一章计划）

| 组 | 去掉/改掉什么 | 验证 |
|---|---|---|
| C0 | 产品全文 | 对照 |
| C1 | 去掉 `mate.system` 的 Tone and style 段 | “plainly and directly” |
| C2 | 去掉 core/world 常驻全文 | 设定复杂度 |
| C3 | 不传工具 schema | 工具调用模式 |
| C4 | 历史只留最近 8 条 | 长历史 |
| C5 | 把“开始写正文”改成“进入叙述，按计划写” | 命令式指令 |
| C6 | 在 prose-window 开头加一句“以下规则覆盖前面的对话语气” | 指令优先级 |

### Phase 3：候选修复

1. **prose 模式覆盖**：在 `<prose-window>` 开头明确写“这一块覆盖前面的 CLI 语气；现在不是聊天，是写小说”。
2. **条件化 mate 语气**：正文窗口打开时，不注入“plainly and directly”这类对话人格句；或把它标成“只适用于对话，不适用于正文”。
3. **resident docs 瘦身**：正文时只给与本章相关的设定摘要，而不是 core/world 全文。
4. **温度**：给正文调用单独 temperature（先测 0.8 / 1.0），不要沿用对话默认值。
5. **范例**：文风卡已有范例；如果 Phase 1 显示 B 仍偏短，再考虑加一段“长句/叙述者态度”的范例，而不是继续加清单。

## 5. 不要先做的事

- 不要因为这一稿直接改写 `style-02-guyan` 卡；文风台证明这张卡本身能出好结果。
- 不要先加“禁止短句”这种负面词；它可能把文字推成另一种匀称的 AI 腔。
- 不要把文风台的 `06-guyan` 当成唯一目标；它只是同卡的一个高冲突场景样本。

## 6. 我建议的第一轮最小实验

只跑 4 组，各 1 篇：

1. A：文风台 + 06-guyan（复现）
2. B：文风台 + 第一章计划（场景）——已经加了 `cases/07-chapter1.md`
3. C：产品 system + 第一章计划（完整栈）
4. C1：产品 system 去掉 Tone and style + 第一章计划（语气冲突）

```bash
# A + B：不用改代码，直接跑
bun run style-bench --case 06-guyan,07-chapter1 --config guyan-base --samples 1

# C / C1 需要把
#   experiments/style-investigation/prompts/chapter1-system.txt
# 作为 system，把 07-chapter1 作为 user 送进 chat；
# 这一步我可以再补一个最小的 investigation runner。
```

如果 B 好、C 差，且 C1 明显变好，第一修复就是“正文时收起 CLI 语气”，不需要动文风卡。

## 7. A/B 第一轮结果（2026-10-25）

输出：[ab-chapter1-3x-20261025-133406](../style-bench/outputs/ab-chapter1-3x-20261025-133406/)

同一 system（六条底线 + `style-02-guyan` 卡）、同一模型（`deepseek-v4-flash`）、temperature 0.8，各 3 篇：

| | A · 06-guyan（退婚局） | B · 07-chapter1（及笄日） | 产品第一章（对照） |
|---|---:|---:|---:|
| 平均句长 | **31.4 字** | **21.4 字** | 21.9 字 |
| 平均段长 | 36.8 字 | 21.7 字 | 22.4 字 |
| 对话开头段落 | 15.3% | 7.3% | 6.3% |
| 样本句长范围 | 30.8–32.3 | 20.7–21.8 | 单篇 |

三点结论：

1. **A 仍然明显比 B 长、比 B 多对话。** 同一张卡、同一套规则，只换场景/计划，句子长度从 31.4 掉到 21.4。第一章的“安静开篇 + 不给爽感”本身就是主因之一。
2. **产品第一章的 21.9 字/句落在 B 的范围内。** 这说明“产品 system 栈”不是解释这稿短句的必要条件；只拿文风台 + 第一章计划，也能写出几乎一样的短句密度。
3. **之前那篇 44.3 字/句的 A 是单样本，没能复现。** 本轮 A 三篇是 30.8–32.3。文风台本身有随机性，后续比较必须看 3 篇均值，不能拿单篇当基线。

但注意：这只解释了“句子变短”。A 的 31.4 仍高于 B 的 21.4，说明场景/计划是**第一层原因**；产品 system 是否还额外压低了“叙述者态度/人际密度”，要靠下一组 C/D 才能回答。

### 下一组最小实验

- **C**：产品 system + `07-chapter1`，看完整栈是否在 B 的 21.4 上继续下降。
- **D**：产品 system + `06-guyan`，看完整栈会不会把 A 的 31.4 也压短。
- **C1**：C 去掉 `mate.system` 的 “plainly and directly”，验证语气冲突。

如果 C ≈ B，而 D < A，说明产品栈主要压的是“有冲突的场景”，不是所有正文；如果 C < B 且 C1 回升，才轮到改 system。

输出：[cd-product-20261025-135617](../style-bench/outputs/cd-product-20261025-135617/)

- C：产品 system + `07-chapter1`
- D：产品 system（去掉 pending 第一章规划）+ `06-guyan`

| | A · 文风台+06 | B · 文风台+计划 | C · 产品 system+计划 | D · 产品 system+06 | 产品第一稿 |
|---|---:|---:|---:|---:|---:|
| 平均句长 | 31.4 | 21.4 | **21.7** | 24.1 | 21.9 |
| 平均段长 | 36.8 | 21.7 | 21.8 | 27.4 | 22.4 |
| 对话段落 | 15.3% | 7.3% | 14.0% | 19.9% | 6.3% |

### C：干净结论

**C 的 21.7 与 B 的 21.4 基本相同，也和产品第一稿的 21.9 基本相同。**

也就是说：对于第一章这个场景，产品 system 并没有在 B 的基础上继续把句子压短。第一章的短句主要是“计划/场景”造成的，不是 18 个工具、core/world 全文或历史把它压成这样的。

C 的对话比例反而比 B 高（14% vs 7.3%），说明产品 system 不是单纯“去对话”；它只是没有把句子拉长。

### D：这组不干净，不能直接下结论

D 的输出开头是：

> 按本书的设定，这场戏落在晋国栾氏：谢云窈即栾氏嫡女伯姬，永康侯府即栾氏……

因为 D 用的是**第一章的产品 system**（核心设定已经是栾氏、及笄日），却喂了另一个项目的人物/场景（谢云窈、退婚局）。模型先花了一段做“改编对齐”，并没有直接演 06 的戏。

所以 D 的 24.1 不能当作“产品 system 把 A 压短”的证据；它测到的是**产品 system 带入了本书设定并改写外来用例**。这是一个真实的干扰，但不是干净的文风对照。

### 需要补的干净 D

要验证“产品写作壳（mate 语气 + prose-window）本身会不会压 A”，应该：

- 保留 `mate.system` + `prose-window` + 文风卡
- 去掉 `design/core.md` / `world.md` 常驻块和第一章 pending
- 再喂 `06-guyan`

这样 D 和 A 只差 mate 语气 + prose-window，不再有“跨书改编”。按现在的证据，**第一优先仍然是改第一章计划/场景，而不是先改文风卡或产品 system**。

## 9. B2：声口优先级能不能压过计划

输出：[b2-voice-20261025-141129](../style-bench/outputs/b2-voice-20261025-141129/B2-bench-chapter1-voice/output.md)

B2 = 文风台 system + 第一章计划 + 一段 `【声口优先级】`：

```md
【声口优先级】
这是小说正文，不是聊天回复。以下优先于计划里压制声音的措辞（例如“不给爽感/只给看清”）：
- 叙述者始终在场，有判断、有态度，不是冷冰冰的镜头。
- 以中长句为主；不要把每个动作切成单独一句。
- 即使场景安静，也要写出在场的人想要什么、在挡什么；心理要落在人与人的关系上。
```

| | B（只有计划） | B2（计划 + 声口优先级） | A（退婚局） |
|---|---:|---:|---:|
| 平均句长 | 21.4 | **28.0** | 31.4 |
| 平均段长 | 21.7 | **29.5** | 36.8 |
| 对话段落 | 7.3% | 5.6% | 15.3% |

**B2 比 B 的句长提升约 31%，段长提升约 36%，已经接近 A 的 31.4。**

这说明：

- system 里的声口优先级**能压过**计划里“不给爽感/只给看清”的措辞；不是完全没用。
- 但它主要修的是“句子长度/叙述者态度”，没有把安静场景变成 A 那种人际交锋（对话仍只有 5.6%）。要拿到 A 的整体故事感，还需要计划里有一个活人场面。
- B2 里仍有一些“清单式”小节，但比 B 的“手/头发/席子”连续短句好很多。

### 候选生产改法

把 `【声口优先级】` 放进 `<prose-window>`（`buildProseBrief`），而不是塞进 `style-02-guyan` 卡：

- 它对所有文风都成立：计划约束事件，不约束声音。
- 不进 `prose.rules` 的“底线”层，避免把“长句/态度”写成跨文风硬规则；它是正文窗口的优先级说明。

下一步应该验证 **C2 = 产品 system + B2 声口优先级 + 第一章计划**，确认放到完整产品栈里也有效。

## 10. C2：把声口优先级放进产品 system

输出：[c2-product-voice-20261025-142131](../style-bench/outputs/c2-product-voice-20261025-142131/C2-product-chapter1-voice/output.md)

C2 = 产品 system + 在 `<prose-window>` 开头插入 B2 的 `【声口优先级】` + 第一章计划。

| | B · 计划 | B2 · 计划+声口 | C · 产品+计划 | C2 · 产品+计划+声口 |
|---|---:|---:|---:|---:|
| 平均句长 | 21.4 | **28.0** | 21.7 | 22.9 |
| 平均段长 | 21.7 | 29.5 | 21.8 | 23.6 |
| 对话段落 | 7.3% | 5.6% | 14.0% | 7.4% |

**同一段声口优先级，在文风台 system 里把句长从 21.4 拉到 28.0；放进产品 system 后只有 22.9。**

也就是说：

- 产品 system 并不是“基准更差”的主因（C ≈ B，21.7 vs 21.4）。
- 但产品 system **会稀释声口指令的效果**：B2 的 +6.6 字/句，到 C2 只剩 +1.2。
- C2 runner 已经不带工具、不带历史，只是静态 system；所以稀释来自 system 文本本身（mate 人格 + core/world 常驻 + pending 计划），不是工具/历史。

### 下一步定位

先做 C3：产品 system + 声口优先级，但**去掉 `design/core.md` / `world.md` 常驻块**，保留 mate + pending + prose-window。

- 如果 C3 接近 B2（28 左右），说明常驻全文是主要稀释源，正文时应该给摘要而不是全文。
- 如果 C3 仍只有 22–23，说明是 mate 人格 / pending / 整个产品 system 结构，需要独立的“正文 system”而不是往产品 system 里追加。

## 11. C3：无效，不能当作文风结论

输出：[c3-no-resident-retry-20261025-143401](../style-bench/outputs/c3-no-resident-retry-20261025-143401/C3-product-chapter1-voice-no-resident/output.md)

C3 = C2 去掉 `design/core.md` / `world.md` 常驻块。

两次输出都不是正文，而是：

```text
<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="bash">
...
```

这是模型在**没有工具 schema** 的情况下，仍然按产品 system 的 agent 身份去“调用工具”。C/C2 能写出正文有运气成分；C3 连续两次跑进工具调用，说明这组实验本身不成立。

### 这反而说明了一件事

产品 system 不是“一段写作文风提示”，它本质上是**一个 agent system**：

- 有工具调用身份
- 有 CLI 语气
- 有项目设定/规划状态
- 有 18 个工具

把“声口优先级”追加到这样的 system 里，效果会被稀释；而把常驻设定拿掉，模型又会回到“调工具”的姿态。**继续往这个 system 里加句子，不是稳定的修法。**

### 下一步应该做的不是 C4 小补丁

真正该试的是：**正文写作时使用一个独立的 prose system**，而不是把 mate 的 agent system 当写作 system。

- prose system：bench 式开头 + 声口优先级 + 文风卡 + 本章计划 + 一份很短的本书/人物 brief
- 工具仍然保留 `write` / `edit` / `read`，但 system 身份是“小说作者”，不是“项目 agent”
- mate 的聊天/规划身份不变

## 15. 两份“计划”的实际差别

用户看到的问题是“章节规划太细”。把 C6 的输入和产品真正生成的章规划并排看，差别非常具体。

### C6 用的退婚局输入

文件：[06-guyan.md](../style-bench/cases/06-guyan.md) · **1,894 字符**

结构只有五段：

- 【题材】
- 【前情】
- 【这场戏】谁在场、在什么地方、她想要什么
- 【必须发生】5 条事件，不写“第几步”“多少字”“放大点”
- 【写法要求】声音、字数、只输出正文

**它不是 `propose-plan` 生成的章规划**，是文风台的场景简报。模型要自己决定：谁先开口、怎么寒暄、把证据放在哪一句、怎么反咬、怎么收。所以对话和场面是它“搭”出来的。

### 产品第一章实际用的规划

文件：[chapter1-plan.md](prompts/chapter1-plan.md) · **12,745 字符**，约 6.7 倍。

结构：

- 意图
- 对应序列与功能
- 价值变化
- 不能提前兑现
- 章末问题
- 产物（按序）
- **步骤与节拍**：五个步骤，每步标“约 500 / 900 / 700 / 900 / 800 字”
- 每步下面：必须立住 / 要过的信息 / 事实 / 不放 / **放大点** / 半句带过
- 执行红线：称呼、器物、动线、年岁感

这份规划把**镜头位置、节奏、每步字数、哪个动作要写几百字**都规定死了。模型拿到它，最省力的执行方式就是“按步骤逐条写”：一步一段、一个动作一段、一句一段。它不是不会写长句，是**没有空间自己搭场面**。

### 关键不是“字数”，是“谁决定镜头”

- C6 的 1,894 字只规定“这场戏必须发生什么”，镜头由模型决定 → 33.9 字/句。
- 12,745 字的规划连“哪个动作放大”都规定了 → 21.9 字/句。
- 1,922 字的修订计划（08）仍然保留了五步、每步拍点 → 28.9 字/句。
- 所以真正要改的是：**规划从“执行脚本”退成“场景简报 + 产物清单”**。产物清单可以细，戏不要细。

### 生产上的两个选项

1. **让 `propose-plan` 输出短简报**：前情 / 这场戏 / 必须发生 / 不能提前兑现 / 产物清单；不写每步字数、不写每步放大点、不写“某动作写几百字”。
2. **保留详细规划做工作单，但正文只喂简报**：planner 可以继续产出细计划，进 `<prose-window>` 时只注入“本章戏”摘要，不把 12k 的执行脚本放进正文上下文。

我更倾向第 2 条：细计划对“执行顺序/产物”有用，对“写正文”是负担。两条可以一起做：细计划留在 plan artifact，正文窗口只拿 brief。
